# MCP Setup

## When to Use This Skill

Use this skill for MCP server configuration, ChatGPT remote connector setup, OAuth/IndieAuth
debugging, and which tools a connection sees (its permission profile).

## Recommended Flow

1. Read `vulcan help mcp-remotes` for client-independent setup, lifecycle, and recovery. For a local harness, use `vulcan mcp --transport stdio` (the default) or direct loopback HTTP. No daemon, browser, or named remote is required.
2. For ChatGPT or another hosted client, register the vault and preview `vulcan mcp remote init <name> --public-url <https-url> --identity <indieauth-url> --dry-run`. Apply it after reviewing the vault, bind address, and ceiling/default profiles. The ceiling must be a built-in such as `writer` or a device-local profile: define one in the device's `daemon.toml` with `vulcan config permissions profile create <name> --target device` (or move a local one with `vulcan config permissions profile move <name>`), never in the synced `.vulcan/config.toml`. On a device whose `daemon.toml` declares the remote, vault (with `source`) and profile, `vulcan daemon plan` then `vulcan daemon apply` sets it up in one step; see `vulcan help device-config`. When the vault itself describes its remote in `[mcp_remote]` of `.vulcan/config.toml`, a device opts in with `vulcan vault set <id> --serve-remote <bind>` and `vulcan daemon apply` instead of `mcp remote init`; `--no-serve-remote` stops serving it. While the opt-in stays, the remote keeps its identity and grants even if the vault's settings break.
3. To expose another registered vault through the same URL, stop the remote and use `vulcan mcp remote set <name> --add-wiki <id> --dry-run`, then apply without `--dry-run`. Use `--wiki <id>` when updating one vault's ceiling or default profile. Start it with `vulcan mcp remote run <name>`, or use `vulcan daemon start --detach` to host configured remotes as resident listeners. Give the client the single public MCP URL printed by init/show. Proxy the MCP path and its `/operations/<id>` subpath, OAuth metadata paths, and `/oauth/*` to that listener. When the proxy runs on another host, set `--bind` to the device's private-network address or a wildcard; named remotes always authenticate, so this does not admit unauthenticated requests.
4. Sign in with IndieAuth, then review and explicitly approve Vulcan's separate consent page. For a remote exposing multiple vaults, explicitly select one vault and its profile; each grant and MCP session stays bound to that selection. Pick the shortest expiry that fits (1 hour up to 1 year, or a last day at most a year ahead); a longer connection is approved again rather than extended. IndieAuth login alone grants no vault authority.
5. Inspect or revoke durable approvals with `vulcan mcp connections list|show|revoke`. Use `vulcan mcp remote set` for deployment changes and `remote remove` to revoke its grants and remove only the device-global definition.
6. The permission profile alone decides which tools are listed: every tool it allows, nothing else. Use `vulcan --permissions <profile> describe --format mcp` to see exactly what a connection with that profile gets, and MCP resources to inspect prompts, skills, and skill commands from the client. To expose fewer tools (a small local model, a read-only connector), choose a narrower profile or a second named remote with one; clients can also switch individual tools off.
7. The `sync_*` tools serve repository-wide Git synchronization diagnostics and appear when the profile has Git access with full-vault read. They are `sync_status`, `sync_doctor`, and `sync_conflicts`, plus `sync_refresh` (start a cycle now: queued on the daemon when it runs, otherwise run directly) and `sync_resume` (clear a paused registration and start a cycle), which need Git access with full-vault read and write. It does not expose conflict resolution or arbitrary Git commands.
8. The Git tools let an agent that works through MCP alone review or commit its own changes. They are `git_status`, `git_diff`, `git_log`, and `git_blame` (Git access plus full-vault read) and `git_commit` (also full-vault write, because it can commit any vault change and runs pre-commit plugin hooks). `git_commit` commits the files named in `paths`, every change with `all: true`, or everything in a changeset; it never guesses, so other writers' edits stay out unless asked for. Its commits carry `Vulcan-MCP-Client` (the self-reported `clientInfo`), `Vulcan-MCP-Client-Id` and `Vulcan-MCP-Subject` (an authenticated remote's OAuth client and owner), and `Vulcan-MCP-Profile` trailers. Writes an agent leaves uncommitted in a vault with batched auto-commit get the same trailers on the batched commit that takes them. Changesets come with them: `changeset_begin` creates a branch and a worktree in Vulcan's user state directory, and note, file, search, query, daily, task, and Git tools work in it when a call passes its id as `changeset` (the server keeps no per-connection state), `changeset_list` lists them, `changeset_land` lands one on the vault's branch (rebase if it moved, fast-forward, re-index) under the vault write lock that sync also takes, and `changeset_abandon` deletes one. Permissions always come from the vault's configuration, never the changeset's copy. Custom skill tools always run on the vault. `note_move` moves or renames a note and rewrites links to it under the profile's refactor grant.
9. A tool call that runs past the request timeout (`--request-timeout`) is not stopped: its result is an `indeterminate` error with an `operation_id`. `operation_get` with that id reports whether it is still running, succeeded (with its result), or failed; check it before repeating the call. Records of calls kept in memory last an hour (256 at most) and are visible only to the caller that made the call; a named remote's writes are in its durable ledger. Over stdio, tool calls also run concurrently, and `notifications/cancelled` drops a call that has not started.
10. `note_set`, `note_delete`, `changeset_abandon`, `task_reminder_remove`, `config_set`, and `file_put` with `overwrite` also need the profile's `destructive` permission. `status` reports the vault, the index, and the connection's effective permissions.
11. In ChatGPT, enable Developer Mode under Settings → Security and login, add the endpoint from ChatGPT Plugins, review the discovered tools, and use the connection's Refresh action after metadata changes. Developer Mode availability depends on account and workspace policy.

## Guardrails

- Do not expose a no-auth public MCP server for a private vault.
- Local stdio and loopback HTTP, with an optional static token, work without the `oauth` build feature. OAuth flags and named remotes require that feature; do not pass `--oauth-local-subject` merely to start local HTTP. For direct IndieAuth, leave that flag unset to use the authenticated identity unless intentionally overriding it.
- Keep Vulcan bound to loopback or a private interface behind the HTTPS front door unless you have a deliberate deployment reason.
- For browser-based local HTTP harnesses, send a valid `Origin` header containing only the scheme, host, and optional port. Vulcan accepts loopback origins (`localhost`, `127.0.0.1`, or `[::1]`) on loopback listeners and the public URL's origin, and rejects origins with paths, credentials, queries, or fragments (403). An accepted Origin does not replace the MCP token or OAuth grant.
- The reverse proxy may forward request bodies length-delimited or chunked, up to 4 MiB. It must pass the public host in `Host` or rewrite it to the listener's IP address (or `localhost` on a loopback bind); any other host name is refused with 421 so a web page cannot reach the listener through DNS rebinding. Repeated `Authorization`, `Host`, `Origin`, `Content-Length`, session or protocol headers fail before authentication or tool dispatch.
- For private development, OpenAI Secure MCP Tunnel is an alternative to exposing a public endpoint. Treat it as a separate OpenAI connection path, not as a Vulcan authentication flag.
- `--tool-pack` and `--tool-pack-mode` no longer exist and are refused; drop them from client configurations and pick a profile instead.
- The vault's skill commands are listed once the vault is trusted on the serving device (`vulcan trust add`). A sandboxed command (`strict`, `fs`, `net`) is callable under any profile its declared profile fits, `writer` included, and runs under that profile; nothing needs `execute`. Check a command as a remote agent will see it with `vulcan tool ci --profile <profile>`.
- Workflow skills appear as `skill://{name}/SKILL.md` resources (with any supporting files beside them): Vulcan's bundled skills in their MCP form, written for MCP tool names, and the vault's own `.agents/skills` as written. A vault skill overrides a bundled one with the same name, and a skill is listed only if the connection can call a tool it names.
- `vulcan://help/tools` lists every tool the connection may call with its arguments, custom tools included; `vulcan://note/{path}` and `vulcan://file/{path}` read vault content under the profile's read permission; `vulcan://agents` is the vault's AGENTS.md.
- [OpenAI's MCP guide](https://developers.openai.com/api/docs/mcp) documents remote MCP behavior and authentication. ChatGPT does not pick up tool changes on its own: use the connection's Refresh action after metadata changes, and retest in a new conversation.
- The sync tools require Git permission and full-vault read permission because its safety reports may name paths anywhere in the repository. A path-filtered read profile intentionally sees no sync tools; use scoped note/search tools or a separately reviewed full-read Git profile.
- `graph_communities` normally persists derived cluster rows and is scheduled as a mutation; set `dry_run: true` for a read-only calculation.
- For `link_suggestion_resolve`, the connection must be allowed to read both endpoint notes and write the suggestion cache. A denied endpoint does not change suggestion state or disclose that note's path.
- If ChatGPT cannot start auth, check issuer metadata, redirect URI, PKCE, allowed principals, and public URL consistency before changing tool permissions.
- If code exchange returns `invalid_grant` after consent, check that the remote still exposes the selected vault and that its profile remains within the ceiling. Correct the policy and start a fresh authorization; do not retry a consumed code.
- An authorization-code response of HTTP 503 `temporarily_unavailable` means the listener has reached its pending-code limit. Wait for unfinished attempts to expire, then restart authorization and consent; do not retry an undisclosed or consumed code or widen vault permissions.
- A browser-authorization HTTP 503 `temporarily_unavailable` means that listener has reached its pending-login or pending-consent limit. Wait for unfinished attempts to expire and start authorization again. A submitted consent transaction is single-use: replaying an approval or denial cannot create another connection.
- Vulcan accepts only its advertised OAuth scopes and requires the authorization `resource` to match the exact public MCP URL. A scope or resource error is an authentication configuration problem, not a reason to widen the permission profile.
- If IndieAuth returns an unauthorized subject, use the subject shown in Vulcan's callback error to correct `--oauth-indieauth-me` or an explicit `--oauth-local-user` binding.
- IndieAuth profile/metadata discovery is bounded and does not follow redirects. If startup reports an identity redirect, set the named remote's identity to the final canonical HTTPS URL; do not extend startup timeouts or weaken HTTPS checks to hide a broken identity URL.
- Reject the consent page if its client, identity, resource, vault, or permission profile are unexpected. IndieAuth login authenticates the person; the separate Vulcan consent action authorizes the MCP connection.
- Named remote definitions are device-global (`[[mcp_remote]]` in `daemon.toml`) and never copied through vault sync. If `daemon.toml` names a `managed_by` owner, CLI edits are refused with the TOML to add to that owner's source; change the source instead of passing `--force-local-edit`, which the next render reverts. Vault permission profiles remain in `.vulcan/config.toml`; grants, refresh-token families, revocations, and per-remote OAuth secrets remain device-local outside the rebuildable cache.
- Named issuer keys and confidential OAuth client secrets use the device-local `SecretStore` with stable instance-bound `file_v1` references. Init/show JSON reports references, never values. If an existing remote needs migration, stop it, preview `vulcan mcp remote migrate-credentials <name> --dry-run`, then apply without `--dry-run`. Preview inspects metadata without reading secret values or writing state. Migration preserves key bytes and client identities; interrupted copies resume only when existing destination bytes match. It retains legacy issuer files as inactive protected recovery material; never delete legacy key files to make startup succeed or bypass a mismatched credential. Public OAuth clients do not need a stored secret. Protected-file custody is not a native keychain or hardware-backed store.
- Established issuer/signing credentials have separate device-local fingerprint receipts. A missing or changed value stops startup instead of rotating keys. Stop the remote and restore the exact protected credential from a reviewed device backup, or preview/apply `vulcan mcp remote migrate-credentials <name>` when its retained legacy source is unchanged. Never delete fingerprint receipts to bypass a missing or mismatched credential; do not recreate the remote as an implicit repair.
- Stop the remote before `remote set` or `remote remove`; the instance lock rejects configuration changes while its listener is running. Restart the daemon after changing definitions to reload resident listeners. `remote set <name> --remove-wiki <id>` removes only that vault and revokes its connection grants and refresh families; it cannot remove the last vault. Use `remote remove` to remove the whole instance.
- When `vulcan daemon plan` reports that a vault's remote asks for a different IndieAuth identity, show the user both identities and let them decide; never run `vulcan daemon apply --accept-remote` yourself, because it changes who may approve connections to the vault.
- A named remote ceiling cannot be `unrestricted`. A connection used or refreshed while its profile is narrower is durably narrowed; widening that profile later cannot restore the grant's former authority. Obtain fresh consent for any expansion, including after restarting the remote.
- A scoped `note_create` grant also applies to template-created files, template moves/renames and their backlink rewrites, and a template-selected final note path. If a template needs paths outside the approved profile, review those paths and obtain fresh consent rather than retrying with a broader server ceiling.
- `notifications/cancelled` targets an in-flight request ID in the same MCP session. A hosted write canceled before dispatch reports its durable operation ID with `dispatched: false`; an already dispatched write may still complete. For an indeterminate write, inspect its `structuredContent.operation_id` status path before retrying.
- MCP list-change notifications on SSE follow the connection's OAuth scopes and read-path grant: a tools-only grant does not receive prompt or resource list changes, and prompt/resource change hints do not reveal edits outside the read-path grant. Request the corresponding scope during consent when that discovery workflow is needed.
- If an SSE stream closes, reconnect and relist the catalogs your grant can read. Vulcan closes a stream whose notification queue fills instead of retaining an unbounded backlog; do not assume every list-change hint was delivered during the disconnect. Revoking a connection grant closes its existing SSE streams and retires their sessions; reconnecting requires a new approval.
- An HTTP 503 with `Retry-After: 1` means that listener is already handling 64 requests (open SSE streams count). Retry after the delay; do not reauthorize or broaden the grant for this transient transport condition.
- 2026-07-28 clients send every request with its own `_meta` and use no session: no `initialize`, no `Mcp-Session-Id`. Their `MCP-Protocol-Version`, `Mcp-Method` and `Mcp-Name` headers, when sent, must match the body (-32020 otherwise). They learn of tool, prompt and resource list changes with `subscriptions/listen`, which first acknowledges the notifications it will send (resource update subscriptions are not offered) and tags each with the subscription id. Over HTTP the listen POST answers with an event stream and closing it ends the subscription; over stdio the notifications share stdout and `notifications/cancelled` naming the listen request's id ends it. Sessions, `initialize` and GET streams below are for 2025-06-18 and 2025-11-25 clients.
- An MCP session expires after 30 minutes without an authenticated request and each HTTP listener admits at most 256 sessions. If an old session ID returns 404, initialize a new session; a 503 with `Retry-After: 60` means the session registry is full, so close unused sessions or retry after the delay.
- Send HTTP `initialize` as a JSON-RPC request with a string or number `id`, not as a notification. Invalid or response-shaped initialization returns 400/-32600 before a session is allocated; correct the request rather than retrying the same payload.
- `note_create` stages `tp.file.create_new` companions from explicit templates and creation triggers with its final ordinary note in one recoverable batch; a failed final-path check leaves those companions unpublished. Retargeting a new note is supported, but creation cannot move an existing note found at the requested path. Existing-note template insertion and creation triggers stage move/rename and backlink effects with their final update; plugin/system-command effects remain outside that batch.
- `task_create`, `task_complete`, `task_reschedule`, `task_reminder_add`, and `task_reminder_remove` recheck their actual resolved write paths against the connection grant at apply time, even after an earlier dry-run plan; a denied target requires a reviewed grant change, not a retry with a guessed note alias.
- Every MCP write result has a `commit` object (`committed` with `sha`, `batched`, or `uncommitted` with a reason). Sync carries only commits, so when setting up a synced vault for MCP-only agents, also set `[git] auto_commit = true` and `strategy = "batched"` in its shared config, or writes never leave the device.
- Resident MCP requests share the daemon's per-vault read/write queue and recheck consent after waiting. Foreground named remotes use the same hosted request boundary. If a call reports an `indeterminate` outcome, keep its `structuredContent.operation_id` and call `operation_get` with it (or query `GET <public-origin><status_path>` with a current bearer token for the same connection grant). The old MCP session is retired. A queued/indeterminate record may still finish; do not retry until status proves it was never dispatched or failed before commit. Known terminal status is retained for 30 days; interrupted or otherwise unknown terminal status is retained for 90 days. After status expires, inspect the vault instead of blindly replaying the write.
- Named MCP startup recovers an interrupted ordinary TaskNotes line-to-note conversion or archive move before accepting requests and refreshes that vault's index. If recovery finds externally edited bytes, startup fails closed: inspect both affected notes with `vulcan repair ordinary-write status` and reconcile them before using the exact transaction ID and review token with `accept-current`. Do not remove the journal or replay the operation blindly.
- A live stdio or HTTP MCP request also refuses a newly pending ordinary-write journal instead of reading a partial conversion or archive. Read requests hold Vulcan's shared vault lock through the response. If the client receives the pending-journal error, use the direct `vulcan repair ordinary-write` commands outside MCP; do not retry the MCP write until recovery or reviewed repair completes.
- Client ID Metadata Documents are accepted only as public HTTPS clients with exact IDs whose redirect URIs pass the same redirect policy as registration. A present `token_endpoint_auth_methods_supported` list must include `none`, regardless of the legacy singular preference; only an absent list permits legacy fallback. Empty or malformed lists fail validation. Vulcan does not support `private_key_jwt` or client assertions. Dynamic registration remains available; do not work around failed client validation by weakening redirect checks or PKCE.
- Client registration is open by default: a redirect URI may be any HTTPS URL, `http` to a loopback address, or a private-use app scheme, without credentials or fragments. A remote's `redirect_hosts` (`mcp remote init|set --redirect-host`, `--any-redirect` to clear) restricts it to HTTPS on listed hosts. An existing redirect query is preserved when Vulcan adds the authorization code; use the exact registered URI during code exchange.
- When the user connects a client, give it the public URL including `/mcp`, and tell the user to check the consent page's "Sends the authorization to" destination before approving; never approve a consent page on the user's behalf.
- A dynamically registered OAuth client must use its declared token-endpoint method: Basic header for `client_secret_basic`, form credentials for `client_secret_post`, or a client ID with no secret for `none`. Do not mix header and form credentials; a method mismatch returns `invalid_client` and is not fixed by changing vault permissions.
- Dynamic registration rejects malformed or duplicate redirect URI entries, unsupported response/grant types, and non-string client metadata instead of silently ignoring them. If registration returns `invalid_client_metadata` or `invalid_redirect_uri`, correct the client's registration payload; do not widen the remote's vault ceiling.

## Example Moves

- Initialize `personal-chatgpt`, run it, inspect the resulting connection, and revoke it without touching the vault.
- Use the long-form direct `--oauth-*` flags only for debugging, external OIDC, or compatibility.
- Debug why `tools/list` does not include a skill command under the selected pack/profile.
- Compare `describe --format mcp` output against the live MCP registry.
