# MDB performance and native integration

Status: accepted implementation direction and acceptance criteria, 2026-09-07. This document defines future work; it does not claim that the current CLI or App host meets these targets. The [MDB implementation contract](IMPLEMENTATION_CONTRACTS.md) controls authorization, revisions, recovery, and feature negotiation. The [Vulcan App v1 contract](../vulcan-app/v1/IMPLEMENTATION_CONTRACTS.md) controls App bindings and transport. These criteria add implementation gates without changing upstream profiles or frozen wire formats.

## 1. Decision and boundaries

Use one mdbase typed-collection model, one Vulcan execution and mutation engine, and multiple frontends. mdbase definitions are the single persisted schema/type/contract format for this App/script collection backend. Its future adoption is uncertain; TaskNotes is one concrete consumer, not a limit on supported uses. Preserve Vulcan's Markdown and collection controls → incremental derivation → SQLite indexes and optimized queries architecture. Build native services beneath the portable model, reusing the existing query representation, permission machinery, and core/app boundary.

Do not maintain a second native typed-collection definition or parallel validation system. Native here describes execution, bindings, and query conveniences over the same collection semantics. Ordinary native note queries remain available with their existing semantics, and untyped Markdown vaults do not acquire a mandatory mdbase marker or schema. An ordinary metadata query must not silently stand in for an mdbase operation that promises defaults, validation, or contract views. Consider an additional native semantic feature only after a consumer demonstrates a gap, with an explicit capability and compatibility review.

Markdown and collection controls remain canonical. Parsed records, membership, effective properties, validation evidence, contract projections, and link indexes belong in Vulcan's rebuildable cache. Durable plans, recovery journals, and reconciliation state retain the separate storage boundary in the MDB contract. A fast cache hit is never authority to omit permission checks or weaken write validation.

## 2. Focused native integration

Use one reusable synchronous collection service. Pure parsing, validation, query planning/evaluation, and cache representations belong in `vulcan-core`; filesystem workflows, refresh, mutation planning/apply, and cross-operation orchestration belong in `vulcan-app`. CLI and App transports adapt these services. Async scheduling and long-lived host sessions stay outside core.

| Operation | Initial integration contract |
| --- | --- |
| Bind and inspect | Resolve an explicitly selected collection within the caller's vault/store scope; expose readable type/contract definitions, effective schema, revisions, diagnostics, and supported capabilities. No ambient filesystem search or schema ownership inferred from a type name. |
| Read | Preserve canonical complete-record semantics, exact-source opt-in, revisions, and permission-filtered diagnostics. Hydrate body/source only as needed and verify consistency with the selected snapshot. |
| Query | Accept canonical mdbase JSON/YAML and preserve its envelope. Native conveniences with explicit collection binding lower to the same physical plan and preserve mdbase membership, defaults, values, diagnostics, and permissions. Equivalent queries receive equivalent indexed optimization regardless of frontend, with residual CEL where needed. |
| Plan and apply | First write pilot: a revision-checked patch to persisted frontmatter. Every collection frontend calls one Vulcan-owned planner/apply service enforcing mdbase type, supported lifecycle, schema, and collection rules plus the MDB authorization/recovery contract. Never treat effective defaults or computed projections as already persisted values. |

The App adapter uses the already specified `stores.mdbase.*` and `mutations.*` operations. Standalone scripts invoke structured CLI commands or shared Rust services without an App package, App instance, or daemon. A direct caller carries its own vault scope and permission grant; it never receives a fabricated unrestricted App context. Shell and Python pilots use supported JSON/NDJSON envelopes, structured arguments/files/stdin where implemented, and explicit exit/error handling. Do not shell out from the App host to implement shared operations.

Retain existing CLI output contracts, including the distinction between successful execution and a validation envelope with `valid: false`. Generate public request/report/error schemas from the operation registry as the corresponding bindings ship. An unimplemented CLI route or App operation must remain explicitly unavailable, not documented as callable. The initial public query request remains canonical mdbase JSON/YAML. Any exposed native-query convenience must specify its collection binding, input/output mapping, capability discovery, and parity fixtures through an explicit versioned API review; this document does not change the meaning of existing `query`, `--json`, or `stores.mdbase.query` requests. A new generic `stores.collections` API or query language is not required.

Deliver read/query/schema first. The patch pilot follows MDB.7; create/delete/rename/batch and declarative lifecycle remain in that track rather than a parallel script-specific write implementation. A working patch pilot does not establish the complete `vulcan.record_write.v1` feature or upstream `core_write` profile. Saved views, automatic subscriptions, runtime activation, SDK generators, and additional collection backends are not prerequisites for this first integration.

### Shared writes and raw-edit boundary

mdbase defines the collection write semantics; Vulcan implements authorization, revision/dependency planning, secure Markdown persistence, journals, recovery, cache publication, and events. All managed collection writes follow one pipeline: authorized revision-bound plan → draft membership and supported lifecycle → post-lifecycle membership and schema/collection validation → dependency recheck and journaled canonical write → coherent derived-state publication → events. Durable plans remain outside the rebuildable cache. Native convenience cannot skip collection rules or write SQLite projections as authoritative data.

Before claiming unified write support, route generic managed structured note/property/task mutations that affect collection records through this pipeline too, including old and proposed membership and multi-record scope. Keep raw-edit/repair behavior explicit and distinguish it from validated collection writes: it may preserve invalid source for repair, but must respect normal permissions, revision/recovery guarantees, invalidate derived state, and report resulting diagnostics without claiming a validated write. Never silently fall back to raw editing when managed validation fails. This routing and its public repair contract are future work, not a claim about current `note`, `update`, `unset`, or TaskNotes commands. External editors remain outside the cooperating-writer boundary; reindex their actual bytes and surface invalid records without silently rewriting them.

## 3. Performance acceptance contract

These are acceptance targets on a documented reference machine, using a release build with pinned build settings. The benchmark artifact must record CPU, memory, storage, OS/filesystem, binary commit/features, fixture seed/digest, cache state, concurrency, request mix, and timings. Select and record the reference machine before claiming a pass; do not change it to conceal a regression.

The primary reference fixture has 10,000 Markdown records, about 4 KiB mean body size, multiple types, a representative TaskNotes-sized schema, and about 100,000 links. Include missing/null/empty properties, defaults, invalid records, and restricted grants. A 100,000-record fixture tests scaling; larger bodies, high link fan-out, expensive expressions, and schema changes are separate stress cases. Mimir remains an optional local validation workload; do not commit private vault contents or paths into benchmark fixtures.

The fast list workload returns at most 50 records and at most 256 KiB of serialized response, with a small selected field set, an indexed type/path/property selection and ordering, and the canonical exact total count. Include task status lists, contact lookups, and project lists. Warm means initialization, schema compilation, and initial indexing have completed, with one coherent current indexed generation and no pending relevant source changes. The compiled plan may be reused; full-result memoization must be disabled for the baseline. Vary predicate parameters and execute queries after updates as well as repeating identical requests.

| Boundary and workload | Acceptance target |
| --- | --- |
| Local App/shared-service metadata query: complete request available at host ingress through authorization, execution, and fully serialized response; excludes browser rendering and remote network transit | p95 < 50 ms; p99 < 100 ms |
| Internal execution component of that query | p95 < 25 ms; explanatory budget, not a replacement for the end-to-end gate |
| Warm single-record metadata read, without body/source hydration | p95 < 10 ms |
| Direct CLI metadata query with existing index and unchanged vault, normal blocking incremental freshness check; process start through final stdout and exit | p95 < 100 ms |

Also report direct CLI `--refresh off` separately; it is not a substitute for the normal-refresh gate. Cold process/host startup, initial indexing, cache rebuild, external-edit reconciliation, source/body reads, and broad control/schema invalidation have separate latency/throughput results. Do not hide them by labeling a stale response warm. No sub-100 ms promise applies to an arbitrary CEL scan, unbounded result, global grouping, or high-fan-out traversal.

Before enabling the writable App/script pilot, benchmark planning, durable apply (including required journal persistence/fsync), derived-state publication, and the following read separately and end-to-end. Record an explicit write acceptance budget based on that evidence. The read gate must not be presented as a write guarantee or met by acknowledging an undurable write. Large batches and cross-vault synchronization are separate workloads.

Run at least 1,000 measured requests per warm workload/mode after a documented warmup. Report p50/p95/p99, sample count, errors, throughput, and memory growth. Test single-client execution and eight concurrent readers with two independent single-record writes per second; concurrent acceptance uses the same read thresholds once that write path exists. Report queueing as part of latency and failures/timeouts as failures, not discarded samples. Serialize benchmark runs on the reference machine. Ordinary CI uses deterministic work assertions and semantic tests; controlled performance runs enforce timing gates and retain baseline artifacts.

## 4. Execution and freshness design

Cache population requires an initialized vault; standalone uninitialized collections remain source-only without query-triggered initialization.

Readers lacking lockfile-read authority retain the existing source-only path: cache dependency verification includes lockfile absence, and optimization must not broaden their grants or inspect a denied control path.

**Collection-wide write validation.** When uniqueness or validated-link rules make a write's validation scope the whole collection, planning and apply-time verification accept unchanged records by the same stat-fingerprint proof as indexed reads: a record whose current stat equals the fingerprint published with a cached revision has that revision without being read, and its cached record-local derivation and body facts stand in for re-parsing. Changed records are always read and derived from their proposed sources, and any record without a matching cached derivation sends the whole analysis back to sources. The proof's limit is the indexed reads' limit: an in-place same-size rewrite within one timestamp tick of an unchanged record is not observed.

**Retained host sessions.** `MdbaseQuerySession` (vulcan-app) is the long-lived host form of the indexed path. The daemon's vault HTTP API serves it as `GET /mdbase/query?query=<JSON or YAML>` and creates it on first use.

- **Retained state.** The session keeps authorized control registries per read scope, compiled plans, pooled read-only cache connections, and decoded indexed rows shared by concurrent requests. It never keeps results or grants. Every request verifies controls.
- **No reader queueing.** Retained execution does not take the vault read lock. A stat-proven result cannot observe a half-applied write, because files and cache rows agree only before a transaction's first replacement or after its cache publication (managed writes publish the record cache before their note scan). While a writer holds the lock, a walk that differs from the retained rows only on paths in that writer's journal, each retained at its journaled pre-write revision, serves the state from before the write; this is linearizable because the write has not completed. Every proof records the version of the retained rows it describes, and any row mutation by another request invalidates it, so a proof's membership is never paired with newer rows. Watched sessions prove each scope single-flight, so requests that arrive during a walk reuse its proof. Any other difference, and any interrupted write (a journal with no active writer), takes the ordinary service with its read guard. Writers pass a writer-preference turnstile, so overlapping readers on that ordinary path cannot starve them.
- **Row reuse.** A retained row is reused only while the request's walk observes the stat fingerprint it was decoded for. Changed rows are decoded again from cache rows whose stored fingerprint must equal the walk's. Residual and persisted-page reads must match the retained revision.
- **In-memory decisions.** Predicates are decided in memory with the same exact rules as the SQL lowering, and a differential test checks both against shared value shapes.
- **Strict policy (default).** Every request walks.
- **Watched policy.** It requires an attached change monitor that ignores derived directories. A scope's last walk proof is reused only while all of these hold:
  - the monitor is healthy;
  - it has reported no notification since before that walk began;
  - the cooperating write epoch is unchanged (it is advanced by every exclusive vault write lock, across processes);
  - the proof is younger than its maximum age (the daemon uses 30 s).

  Cooperating writes are therefore observed immediately, and external edits once their notification is delivered. Watcher errors or rescans fall back permanently to strict walks.

The [10K session diagnostic](measurements/shared-query-session-10k.json) used 1,000 samples per mode on a loaded development host, at the in-process service boundary (no HTTP):

| Policy | Unrestricted p95 / p99 | Restricted p95 / p99 |
| --- | --- | --- |
| Watched | 23 / 26 ms | 21 / 25 ms |
| Strict | 71 / 86 ms | 69 / 86 ms |

The watched figures sit within the shared-service targets; reference-host acceptance, concurrency, and HTTP-boundary measurement remain open.

**Indexed metadata reads (schema v23, record model 8).** The public query service first tries an indexed path and falls back to the disk-reconciled path below on any doubt.

- **Freshness.** Freshness is proven by stat fingerprints rather than content hashes. A fingerprint is a record's device, inode, size, mtime, and ctime. Refresh captures it with fstat on the same descriptor before and after reading the bytes it hashes, so a stored fingerprint always describes exactly the cached revision. Ordinary tools can restore mtime but not ctime, so a same-size edit with a restored mtime still invalidates the row. Off Unix no fingerprint exists and the path declines. Refresh publication itself remains content-verified.
- **Storage.** Per-record query data lives in a narrow `mdbase_record_query` table: revision, dependency digest, model, fingerprint, CEL input evidence, JSONB effective frontmatter, and file metadata. It is kept apart from the wide row because overflow pages from body-bearing payloads made every column read touch them. Triggers delete a narrow row whenever its wide row changes or disappears.
- **Snapshot.** One parallel discovery walk stats every visible record, using directory-relative stats that do not follow a final symlink. The walk is merge-joined with cached fingerprints inside the same SQLite read transaction that serves every later read. A record changed before its stat mismatches and forces fallback; one changed after it is a later change. The result therefore equals the vault at an instant during the walk, with no second walk. Controls are verified against the cached dependency digest first.
- **Execution.**
  - SQL decides a lowered predicate exactly when every atom's JSON type is one the lowering decides. Each atom's type and value are computed once per candidate. Only undecided rows (missing, null, wrong-typed, or NUL-bearing values) run the same CEL filter on their cached local record, which preserves ordinary diagnostics.
  - Ordinary execution checks CEL input bounds for every type candidate, so refresh stores per-record binding evidence: conversion success, bytes, nodes, and width. Evidence is computed from the unrestricted post-overlay record. Link resolution, the only scope-dependent part, is bounded per link by the longest collection path. A candidate whose evidence cannot prove the limits declines the indexed path.
  - Ordering uses the ordinary comparator over keys extracted in SQL, and only the returned page is hydrated.
- **Eligibility.** Plans with named projections, invocation context, grouping, summaries, bodies, expression selections, unlowered filters, or clock-dependent inferred membership decline. Restricted readers evaluate JSON only for visible rows and never write the cache.

Differential tests compare the indexed results with source-derived execution, covering defaults, wrong types, NUL strings, large integers, aliases, persisted/effective modes, restricted scope, and residual diagnostics. Further tests cover fallback on stale, new, or deleted records, on control changes, on over-limit inputs, and on inferred types.

The [indexed 10K CLI diagnostic](measurements/cli-10k-indexed-query.json) uses the validating driver on a shared development host, not the reference machine. Before this work the ordinary path measured p50 2.78 s and about 450 MiB peak RSS. With it, 45 repeated requests per mode had these p95s at about 97 MiB:

- unrestricted, blocking refresh: 63 ms;
- restricted: 80 ms;
- `--refresh off`: 85 ms.

A second unrestricted run during host load spikes reached 125 ms at p95. Every result passed the driver's exact-total, ordering, and bounds checks. These are diagnostic observations, not acceptance: the reference host, 1,000-sample protocol, concurrent writers, 100K scaling, and the service-level 50 ms gate remain open. Each process still pays a cold envelope-validator compile, and every request still pays a full stat walk.

Public query integration now uses a conservative disk-reconciled path: capture visible source hashes and same-descriptor metadata, reuse matching local cached rows, and compare the manifest and consumed record revisions after preparation. Unrestricted readers may refresh or rebuild derived rows; restricted readers open SQLite read-only and fall back to authorized source records without publishing a partial collection. Cache unavailability does not prevent source evaluation. This supersedes the source-only status of the earlier component milestones below, but does not complete indexed physical query execution: all visible sources are still hashed, bodies hydrated, and collection overlays recomputed. Both CLI refresh modes retain this reconciliation; no warm latency gate is claimed.

SQLite-backed physical execution is an architectural requirement for the common collection-query path, not an optional optimization after an in-memory engine is established. Prepare mdbase state when source dependencies change, then query a consistent indexed snapshot. Cache refresh must discover and rederive changed records and affected dependents, rather than rederive the whole collection and merely avoid unchanged SQLite writes. The record cache now reuses unchanged record-local derivations without reading their sources when the same-descriptor stat fingerprint and revision match, verifies them by fingerprint, and rewrites only changed rows; when indexed execution misses on freshness, unrestricted readers refresh incrementally and retry the indexed path. When no record is added or removed and every changed record keeps its identity facts (types, basename, authored ID, uniqueness values; stored per query row since schema v24), refresh re-overlays only the changed records, because other records read them only through those facts. Other changes still decode previous local payloads and recompute collection-wide overlays. Managed writes publish the cache after commit, so cooperating writes keep indexed reads current for restricted readers too.

Schema v20 adds a rebuildable `(collection_root, type_name, path)` membership index, backfilled without rewriting existing projections and maintained transactionally with them. Core candidate selection uses the existing structured plan's type set with ASCII case-insensitive membership, parameterized SQL, and permission-filtered path output. Tests assert a membership-first physical plan and bounded SQL work on 10K cached rows. This is a selection primitive, not a public query executor: callers still need a complete coherent current cache snapshot and control authority, and must evaluate remaining predicates, diagnostics, totals, sorting, groups, and pagination. Cached cross-record diagnostics cannot be copied across permission scopes. Public queries can now reuse disk-reconciled cached records as described above; type/scalar/path SQL lowering, selective hydration, retained freshness tracking, and end-to-end performance evidence remain outstanding.

Index collection/type membership, path selection, and measured high-value property filters/sort keys, retaining enough persisted/effective/presence information to implement mdbase semantics. Preserve source revisions, dependency versions, and validation evidence. Do not eagerly index every arbitrary frontmatter combination. Extend the existing shared query representation with a physical execution plan rather than a second public AST.

Schema v21/model v6 additionally retain authored frontmatter and file metadata in a separate nullable metadata payload. Migration does not infer persisted values from effective defaults; legacy and missing payloads are cache misses until source-derived refresh. Metadata-only changes update cached file values while content revisions remain byte-derived. Rebuild avoids parsing obsolete payload JSON and can regenerate corrupted metadata/effective/diagnostic payloads without rewriting notes. This payload is not a complete record or permission-safe query snapshot: body/source and authorized links are still separate work, and cached cross-record diagnostics remain scope-sensitive.

Schema v22 stores a separate nullable record-local payload before uniqueness, link resolution, and contract overlays. Refresh reuses its parsing/type/schema result only when content revision, file metadata, model, and control dependency digest match; missing payloads derive from source, and rebuild ignores damaged payloads. CEL inference currently disables local reuse conservatively because its clock dependencies are not yet classified. Final collection overlays are always recomputed, so changes to other records cannot preserve old link/uniqueness diagnostics. Work counters distinguish local derivation from reuse. Metadata read/candidate APIs never select the body-bearing local payload. This is partial incremental preparation only: refresh still reads/hashes all sources, hydrates all local payloads, and recomputes all overlays; public queries now reuse these local payloads after disk reconciliation, while residual evaluation remains in memory.

The core cached-record-set loader can reconstruct a visible collection from one SQLite snapshot using a caller-proved current revision/metadata manifest. Permission checks precede payload fetch/decode, and visibility-sensitive overlays are recomputed rather than reused. Missing/stale payloads and dynamic CEL membership fall back; denied corrupt payloads are not inspected. This avoids record-file reads inside the helper, but still reads controls, hydrates every visible body, and recomputes global overlays. The helper itself cannot establish manifest completeness or freshness; the App caller now supplies disk-reconciled manifests as described above. No warm latency gate is implied.

Record model 7 adds raw body link/tag parse facts to the private local-cache payload, without changing canonical record envelopes or the schema-v22 table layout. Unchanged local records reuse those facts during refresh and cached query overlays instead of reparsing Markdown bodies. Target resolution, frontmatter link rules, uniqueness, contract projections, and diagnostics are still computed against the current visible snapshot. Old model rows rederive; missing or malformed required facts cannot silently become an empty link set and remain repairable from sources. This does not avoid body hydration, source hashing, or full visible target resolution, and is not performance acceptance evidence.

Before publishing a refresh or rebuild, the current conservative path rechecks derived records against disk content revisions and file metadata, then checks discovered record membership and control snapshots. Observed record drift fails before any cache transaction, preserving old rows; same-size edits with restored mtimes cannot pass on metadata alone. Stable retry reconciles disk. This rereads sources and does not implement warm indexed reads. It also does not lock out external filesystem editors after verification; cooperating mutation locks and retained generation/freshness integration remain required.

Compile each distinct CEL expression once per prepared plan and each schema once per relevant control revision. Share immutable link/schema data; never deep-copy the collection link index per candidate. Classify query dependencies and avoid body/link/contract hydration for queries that do not use them. Keep query-level clocks fixed, and invalidate or reevaluate time-dependent projections correctly; plan reuse does not freeze `now` or `today` across operations.

CEL resource accounting now borrows existing JSON bindings instead of cloning them into a second root value. The same compact JSON serializer writes to an exact byte counter rather than retaining an encoded buffer; node and collection-width traversal retains its original order, including the bindings-map root. Byte-limit errors still report the full serialized size, and unused bindings remain checked before interpretation and converted as before. This reduces accounting allocations only: it does not omit input data, cache permission-sensitive bindings, or establish a performance gate.

Query execution now constructs its CEL link index lazily, once per operation, only when an evaluated record expression contains a `link()` or `asFile()` call. The dependency is retained with the compiled program; it is not inferred from literal text or a branch's current result. Unused selections and type-filtered/empty collections do not force index construction or earlier compilation errors. The index belongs to the current authorized record set, not the reusable prepared plan. This avoids a second whole-collection file/body/link/tag snapshot for ordinary metadata expressions while preserving complete CEL input-bound checks and diagnostics. It does not avoid source reconciliation, record hydration, collection overlays, or per-candidate file bindings, and establishes no latency gate. Lifecycle authorization classification and summary contexts are unchanged.

The [public 10K lazy-index comparison](measurements/cli-10k-lazy-link-index.json) measures release builds `16f42165` and `56c29cdb` on the same fixture and development host, with unrestricted runs in before/after/after/before order and a restricted before/after pair. All 60 requests preserve exact totals, ordered paths, response bounds, and source bytes. Across 18 repeated unrestricted requests per build, median wall time changes from 3.68 to 3.18 seconds and maximum child peak RSS from about 514 to 287 MiB. Nine repeated restricted requests per build change from 3.29 to 2.95 seconds and about 465 to 190 MiB. These are diagnostic observations under uncontrolled host conditions, not 1,000-sample reference-machine acceptance, retained-memory growth, or concurrency evidence. Every measured query remains multi-second; selective SQL execution and retained freshness remain required.

The initial indexed-read milestone must include parameterized SQL lowering for the proven subset of type membership, path prefixes, scalar comparisons, conjunctions, field selection, and ordering used by the acceptance workloads. Express relational work as SQL so SQLite can optimize it; fetching all records and evaluating an opaque CEL predicate per row is not sufficient. Extend the subset only with equivalence evidence, retaining residual CEL for expressions that cannot safely lower. Preserve missing/null distinctions, effective defaults, numeric and date behavior, explicit/inferred membership, evaluation errors, diagnostics, sorting, and pagination. Index selection must not silently remove records whose evaluation has observable required diagnostics. Exact `meta.total_count`, residual filters, and grouping may require evaluating all candidates: do not push `limit` before those semantics or return approximate totals under the existing envelope.

Compiled CEL programs now retain conservative scalar candidate predicates derived from the same parsed AST: direct effective fields (including `record`/`note` aliases), `file.path`, string/boolean/signed-integer comparisons, literal string prefixes, and up to sixteen conjuncts. SQL values are bound parameters; unknown/missing/wrong-typed values and NUL-containing strings remain residual candidates. Unsupported syntax, floating/unsigned/null literals, nested fields, and dynamic values stay residual. Canonical prepared-query access reuses existing programs without forcing lazy structured-query compilation and declines plans with pre-filter named projections or invocation context. A core selector combines these predicates with type membership in one SQLite read transaction; an explicit lazy `CASE` authorization guard prevents evaluation of denied JSON payloads. Differential tests cover CEL matches/errors, defaults, binary string/prefix semantics, large integers, injection-shaped values, hidden corrupt payloads, and no premature pagination. The public integration below now uses this selection primitive, but does not establish selective hydration, indexed-property execution, or performance acceptance.

The shared public query service selects candidates and loads local records in the same SQLite read transaction, retaining both in an immutable query-plan-bound snapshot. Before enabling pruning it verifies scalar-column agreement with decoded payloads and type-index agreement with the visible record memberships; inconsistent projections or selector failures retain ordinary residual evaluation. After the existing source/control rechecks, execution visits type-eligible records in their original order. SQL-rejected records still construct complete CEL bindings, validate resource bounds, and perform binding conversion; only predicate interpretation is skipped. All visible records remain available for scoped overlays and link-dependent selections. Source fallback, unsupported filters, named projections, invocation context, and query-plan mismatches remain residual. Work metrics distinguish SQL selection, type candidates, input checks, and predicate executions without changing canonical envelopes. Tests cover source parity, filtered-out link targets, inconsistent cache projections, oversized rejected records, restricted scope, and failure order. This intentionally still hydrates all visible bodies and performs full-source reconciliation; cached input-bound evidence, selective hydration, property indexes, selection/order lowering, frontend parity, and the full latency gates remain open.

Canonical mdbase queries and collection-bound native equivalents must share selection/index opportunities and satisfy the same workload latency gate. The native frontend may offer simpler authoring, but canonical CEL must not be confined to a slower interpreter path for equivalent supported expressions. Include normalized physical-plan and SQL/index-use evidence alongside timings; small frontend parsing overhead need not produce identical wall-clock samples. SQL is an internal implementation detail, not ambient SQL authority for Apps or scripts.

For the steady-state metadata-list baseline require zero Markdown body/source reads, zero schema compilations, zero full collection rederivations, and zero per-candidate whole-index clones. CEL compilation counts must be bounded by distinct expressions for a new plan and zero for a reused plan. Instrument candidate counts, rows visited/hydrated, and dependency work; the indexed selection must avoid visiting unrelated record bodies as fixture size increases.

The shared Rust query service now has an explicit diagnostic metrics entrypoint over the ordinary execution path, without changing canonical CLI envelopes. It measures control loading, canonical preparation, source-manifest reconciliation, cached SQL/decoding, collection overlays, refresh/fallback, and residual execution. Counters include only authorized decoded/overlay records and completed visible manifests; collectors reset before authorization and preserve partial failure timing. The [developer stage benchmark](measurements/FIXTURES.md#shared-service-stage-diagnostics) includes per-request permission resolution and compact response serialization. These diagnostics are not complete source-read, schema/CEL compilation, candidate-work, or syscall instrumentation, and do not establish any acceptance gate.

Unrestricted repeated requests average 3.36 seconds: 1.11 seconds in two source manifests, 0.18 seconds in SQLite/decode, 0.89 seconds in collection overlays, and 1.10 seconds in residual execution. Each request hashes 20,000 record instances and decodes all 10,000 cached records, including one-contact lookups. Restricted requests average 2.64 seconds and still hash 18,000 visible instances and decode all 9,000 visible records. Every request uses one cache hit without refresh or fallback. Thus source reconciliation, collection-wide processing, and residual execution all require substantive optimization; compilation-only changes cannot close the observed gap. Source/executable hashes and fixture digests identify this uncommitted-source measurement precisely. This development-host diagnostic excludes process startup and is neither a controlled comparison with prior CLI runs nor reference-host acceptance evidence.

A host retains collection sessions, compiled plans, registries, and prepared statements with bounded memory/eviction. Direct CLI uses the same persistent cache and synchronous services without requiring that host. Cache generations and plan identities bind applicable record-model, schema/control, engine, query, and permission dependencies. Recheck effective authorization on every operation, including cached plans; apply visibility before evaluation, totals, grouping, pagination, link resolution, and diagnostics. Shared unrestricted indexes must not become permission-filtered answer caches.

Read one coherent generation. Cooperating Vulcan mutations publish derived state or make dependent reads wait/reconcile before successful following reads; errors cannot expose a partly applied batch. External filesystem edits are discovered through watching and reconciliation, with explicit freshness policy. A strict disk-reconciled read may wait for a scan and is timed accordingly. Missed watcher events must remain repairable. Do not silently replace strict freshness with stale reads to achieve the target. Keep internal generation bookkeeping out of canonical envelopes unless an explicit versioned API extension is reviewed.

## 5. Delivery and evidence

The [80-request borrowed-input comparison](measurements/shared-query-borrowed-input-10k.json) records eighteen repeated requests per build/scope in before/after/after/before order. Mean request time is 2.68 versus 2.54 seconds unrestricted and 2.59 versus 2.31 seconds restricted; execution-stage means are 1.06 versus 0.86 seconds and 1.01 versus 0.76 seconds respectively. Every checked result and the fixture digest remain unchanged. The first baseline request includes a model refresh left over from the earlier comparison and is excluded from repeated statistics. Host/order variation remains visible, and the checker still serializes/counts all input and converts all bindings. These development-host observations neither pass the reference latency gates nor prove them unreachable.

A [production CLI 10K source-path probe](measurements/cli-10k-source-path-probe.json) at commit `6a3075a1` returned the correct 50 rows / 1,556 exact matches in 27,344 bytes, but took 9.35 seconds initially and 6.0–6.8 seconds over six repeated requests, with about 555 MiB peak child RSS. Both `--refresh blocking` and `--refresh off` use source-derived execution here: MDB commands are not in the ordinary cache-refresh dispatcher, so the latter does not switch to cached reads. These seven diagnostic samples are not the required warm indexed acceptance workload or evidence of unreachability. They establish that component improvements have not closed the full-path gap and prioritize coherent incremental SQLite-backed read/query integration. Stage timings, varied/restricted workloads, designated reference host, and full acceptance runs remain outstanding.

A [post-integration 10K diagnostic](measurements/cli-10k-cached-query-probe.json) at `16f42165` uses the repeatable CLI driver across all nine fixture queries, unrestricted blocking/off and restricted blocking. All 30 requests preserve exact totals, ordered paths, response bounds, and fixture bytes. First cache population takes 10.56 seconds; repeated blocking requests take 3.35–4.04 seconds, off requests have a 3.59-second median, and restricted requests take 2.98–3.32 seconds. Even single-contact lookups retain multi-second cost. Peak child RSS is about 516 MiB unrestricted and 465 MiB restricted. These nine repeated samples per mode are not a reference-host or 1,000-sample acceptance run, and the changed query mix/host conditions do not support a controlled speedup claim against the earlier probe. Both refresh arguments still perform disk reconciliation. The remaining gap prioritizes selective physical execution, dependency-aware hydration, and retained freshness; no target is declared unreachable.

Deliver these slices as separate working changes:

1. **Baseline and instrumentation:** deterministic public fixtures, native/DQL/mdbase comparisons, stage timing/work counters, explicit current limitations, and the reference-machine benchmark artifact.
2. **Repeated-work removal:** CEL/schema compilation reuse, shared link state, and dependency-driven hydration. Remeasure each change; do not presume this removes whole-collection preparation.
3. **Incremental SQLite execution:** real changed-record/dependency updates, permission-safe snapshots, cache integration, and the initial SQL lowering subset with indexed selection/order. Establish the warm read gate in direct mode before waiting for the full App platform; merely caching whole-collection loads does not complete this slice.
4. **Focused bindings:** a shell task-list script, a Python read/query/validation integration, and Collection Studio read/schema/query views use the same semantic services. Add explicitly reviewed native query conveniences with cross-frontend semantic/plan/performance parity, preserving existing unbound native-query behavior. App acceptance follows Phase 19 host availability; standalone scripts do not depend on it.
5. **Unified writes and live-state gates:** use MDB.7 for the status-patch pilot, shared routing of managed collection edits, explicit raw repair, and write budget/recovery evidence; use MDB.9 for subscriptions and sustained read latency under edits. Further SQL lowering beyond the required initial subset follows measured need and semantic parity.

Differential tests compare the optimized path and equivalent collection-bound frontends to the source-derived evaluator using identical source snapshots, operation clocks, permissions, and query parameters. Compare record sets, persisted/effective values, contract views, exact-source opt-in, diagnostics, ordering, totals, groups, and errors. Verify equivalent patches through App, script, mdbase, and generic managed entrypoints have the same accepted bytes, validation failures, lifecycle effects, and revision behavior. Include explicit raw repair without silent fallback, external edits, same-size changes with misleading mtimes, renamed/deleted records, new matching types, local schema-reference changes, permission revocation, clock/timezone changes, phantom uniqueness conflicts, crash recovery, and full cache rebuild. Performance cannot justify dropping unsupported-syntax diagnostics, validation, or authorization.

First-party App-backend readiness requires the read performance and parity gates; writable readiness additionally requires the existing MDB mutation contract and explicit write budget. Read-only exploratory CLI use may continue while the gates remain unmet. No gate claims a new upstream profile, removes optional profile requirements, or blocks unrelated daemon work. Review installed assistant guidance when callable behavior actually changes; planning documents must not teach unimplemented commands.

Component evidence: [pinned control-envelope validator reuse](measurements/envelope-validator-reuse.json) records a serialized release comparison of compile-per-file and retained validation, with 1,000 samples per schema/mode. The two bundled validators are process-wide; user schemas remain authorized collection snapshots. This measurement excludes the query/CLI boundaries, 10K/100K fixtures, memory growth, and concurrent writes, and does not establish any acceptance gate.

[CEL link-index sharing](measurements/cel-link-index-sharing.json) measures function registration against a prebuilt 10,000-target in-memory index. Registration now captures the caller's original immutable `Arc` instead of copying all targets per expression; each evaluation still owns a fresh traversal budget. This removes that specific per-evaluation whole-index copy, not whole-collection loading, eager index construction, or repeated CEL compilation. The component fixture has no links and is not the public Markdown acceptance corpus; no end-to-end gate is established.

[Prepared execution programs](measurements/prepared-query-programs.json) compare compile-per-candidate execution with reusable programs on 100 prebuilt records. `MdbasePreparedQuery` owns the existing structured plan and lazily compiles each distinct execution expression once, including shared sources across projections, filters, selections, and summaries. Each execution still receives fresh authorized records/types and a fresh clock, builds its link index, and evaluates candidates; it retains no results or authority. The one-shot executor uses the same path. This component measurement predates canonical preflight integration and does not establish host retention, SQLite lowering, hydration, or acceptance-workload requirements.

Canonical preparation now offers `compile_mdbase_prepared_query`, which retains the distinct programs used by eager syntax validation and dependency ordering. The shared App query report executes this prepared object instead of discarding and recompiling those programs. Tests count one compilation per distinct source across all preflight roles and zero additional compilations during repeated execution, including after an empty first execution; diagnostic locations, totals, groups, and fresh clocks remain covered. Preparing an existing structured plan still compiles lazily to preserve its execution error ordering. No records, results, or authority are retained, and this change has not yet been measured at the end-to-end acceptance boundary.

Collection link derivation now builds a compact index of authored IDs, paths/types, and basename candidates from the supplied visible record set. It no longer copies complete records or scans every record for each link target/type check. Filename selection visits matching basenames only, preserving same-folder, shortest-path, and lexicographic precedence; duplicate IDs remain ambiguous. The [lookup component comparison](measurements/link-target-index.json) isolates ten path lookups against 10K prebuilt records. It excludes index construction, body parsing, source loading, authorization, and query execution/serialization, so it is not an end-to-end gate. Whole-collection body parsing, incremental invalidation, retained snapshots, and SQL query execution remain open.
