# MDB implementation contract

Status: normative Vulcan integration decisions for the remaining MDB.6–MDB.10 work, reviewed 2026-09-07. The pinned upstream artifacts remain authoritative for upstream format/profile semantics. This document specifies Vulcan authorization, transactional guarantees, and native feature negotiation; it does not silently amend an upstream conformance claim.

The [performance and focused native integration contract](PERFORMANCE_AND_NATIVE_INTEGRATION.md) adds MDB.10 acceptance gates for indexed reads, App bindings, and standalone scripts. It retains the portable mdbase model and existing wire contracts; documented targets do not establish implemented capability or performance.

## 1. Profile evidence and delivery dependencies

Use the immutable revision and tree digest in `vulcan-core/resources/mdbase/v0.3/PROVENANCE.md`. Evaluate every profile against both its normative requirements and pinned coverage ledger; passing fixtures is necessary, not proof that an empty or draft requirement set is complete. Record upstream profile, exact revision, covered requirements, supplemental tests, unsupported features, and known gaps separately in machine-readable evidence.

The pinned `tests/manifest.yaml` marks `links`, `core_write`, and `lifecycle` draft. In particular `core_write` lists managed type-pack preflight, provenance, concurrency, adoption, diff, idempotency, and atomicity requirements, although type-pack installation is deferred by Vulcan. Do not advertise `core_write` after implementing record CRUD alone. Either explicitly promote and implement every required type-pack behavior or review a new upstream pin before claiming that profile. Do not edit bundled upstream fixtures to make a claim pass.

Bounded record CRUD may ship first as the Vulcan-owned feature `vulcan.record_write.v1`, with `core_read` and `collection_semantics` prerequisites. Its contract is sections 2–5 below and MDB.7's draft/lifecycle pipeline. Declarative lifecycle support is separately advertised as `vulcan.lifecycle.v1` after its CEL dependency and provider tests pass. Named views use `vulcan.saved_views.v1`; `.base` adaptation separately advertises `obsidian_bases_views` only with the required oracle evidence. These names are feature claims, not invented upstream profiles. Apps negotiate profile and feature names explicitly and report which namespace a claim belongs to.

MDB.6 owns link resolution/helpers; MDB.7 owns record writes and declarative lifecycle; MDB.8 owns saved views, `.base` adaptation, and explicit TaskNotes migration. MDB.9 owns watcher integration. Studio's first-party read-only backend requires MDB.4/5 and the MDB.10 read acceptance gates, with no saved-view default until MDB.8; linked pickers require MDB.6, writes require MDB.7 and MDB.10 write acceptance, saved views/import migration require MDB.8, and automatic refresh requires MDB.9. Missing optional features disable their controls, not unrelated reads. No MDB slice becomes a global daemon gate.

## 2. Authorization and constraint scope

Apps, native scripts, canonical mdbase commands, and generic managed edits to collection records use one Vulcan mutation pipeline enforcing the same mdbase semantics. Native frontends do not get a separate validator or a direct authoritative SQLite-write route. The [shared-write and raw-edit boundary](PERFORMANCE_AND_NATIVE_INTEGRATION.md#shared-writes-and-raw-edit-boundary) requires explicit raw repair, no silent fallback after validation failure, and cross-entrypoint parity before unified write support is claimed. Generic note/property/task and script mutations now route through shared App planning; complete control-dependency authorization remains open.

Keep current read filtering before validation: a filtered read describes only readable records and must not disclose hidden uniqueness relationships. Do not reuse that filtered result as write-integrity evidence.

The six shared MDB read/report surfaces now authorize `mdbase.yaml` before opening it, require complete coverage of configured type/contract namespaces before discovery, and authorize each control/schema path before reading it. Schema denials abort the registry load with a generic `permission_denied`; they cannot be reduced to invalid-type diagnostics and omitted. Registry-only discovery no longer crawls ordinary records. App write planning and apply now use that same ceiling before loading controls, also requiring read authority for `mdbase.lock.yaml` even when absent. Registry reloads, lifecycle recaptures, and both transaction dependency rechecks retain the filter. Profiles with dynamic policy hooks fail closed because complete namespace visibility cannot yet be proved. Recovery-service authority and retained-session authority checks remain open.

Shared App managed-write routing now checks `mdbase.yaml` read authority before observing presence or parsing contents, including ordinary paths, dry runs, and explicit raw repair. Note/template routing and ordinary-write rechecks carry the selected profile; guarded task APIs carry the caller's profile and reject a changed resolved selection rather than borrowing the default grant. Property routing uses its resolved guard and rechecks ordinary membership before writing under the lock. Script committers use their configured profile and propagate routing failure without ordinary fallback. Absence and denied malformed contents produce the same generic denial. Authorized absence or excluded paths still select the ordinary workflow without loading type/contract registries. Structured CLI task mutation handlers and automatic archive/pomodoro transitions now forward the selected guard; transport regressions cover control/path denial and collection-wide constraint-scope denial without hidden-conflict disclosure. External-editor launch authorization and read-only task-report coverage remain under audit. This is not proof of complete retained-session, recovery, dynamic-policy, or all-entrypoint authorization integration.

Scope discovery includes incoming constraints declared by other types: collection/path-scoped uniqueness can compare an untyped candidate, and constrained links can target it. These rules require namespace coverage even when no changed record matches their declaring type. Only type-scoped uniqueness is limited to the union of old and proposed memberships across the affected records. Do not read existing owners or inbound links to decide whether a namespace proof is necessary.

A write planner computes the full validation dependency scope from collection config, matched types/contracts/schemas, uniqueness scopes, link constraints, rename references, and candidate paths. Before evaluating record-dependent constraints it verifies that the caller can read every relevant dependency and can write/delete every affected path. Prove read coverage over the rule's potential path namespace from policy, not only currently discovered records: type-wide uniqueness requires coverage of the collection candidate namespace, even if it is currently empty. Do not inspect hidden type membership or record existence to narrow the required grant. If selector coverage cannot be proved conservatively, deny the write. If complete scope visibility cannot be established, return `permission_denied` without probing whether a hidden record actually conflicts. The same restriction applies even when the candidate value happens to be unique. Do not return hidden paths, counts, values, or conflicting IDs. This conservative rule intentionally makes some narrow app bindings read-only; it does not grant read authority implicitly or add a uniqueness oracle.

An unrestricted local user or separately authorized service may plan the operation under its own explicit grant. A browser invocation never silently borrows that grant. Type/control/schema mutation requires dedicated control-path write authority and preview; ordinary record writes cannot alter validation rules. Apply rechecks grant lineage and both old/resulting record selectors. Link resolution, inferred membership, and CEL helpers use the same authorized scope; unavailable controls cannot be silently treated as absent.

The core compiled-schema snapshot API captures exact transitive local reference bytes independently of filename extension and authorizes each base/reference path before inspecting it. Snapshot validation performs no filesystem or network access. Secure local reference reads reject symlinked files and parent directories and enforce byte bounds on the opened descriptor. Callers own the supplied base-schema revision and must recheck authority and dependency revisions before reuse across operations. Wiring these immutable snapshots into complete App control loading, revision tracking, and retained collection sessions remains required; exposing the primitive does not establish that authorization or performance gate.

Type registries retain one compiled record-schema snapshot per valid type and share it across registry clones. Record reads, proposed-source analysis, and lifecycle draft validation use that snapshot without reopening or recompiling type schemas. Contract registries similarly retain each subject schema for binding and projected-view validation, and implementation field checks use the existing resolved type snapshot without rereading its sources. Wrapper introspection comes from the same captured reference bytes as validation. Nested file references use the containing schema's directory. Type and contract wrapper fragment selection precedes compilation, preserving the selected-schema local-pointer root required by the pinned core fixture; this is distinct from ordinary JSON Schema `$ref` fragment resolution. Loading a new registry observes control edits. Full control authorization/revision coverage and host-session invalidation remain open. Portable digest handling for transitive external references also needs audit before those digests can authorize retained application bindings. A complete reference-profile audit must cover `$id`, URI encoding, optional-feature negotiation, canonical `schema_ref_*` diagnostics, and the pinned profile's symlink rules before claiming full reference interoperability.

## 3. Plans, revisions, and deterministic values

Cache population requires an already initialized `.vulcan` directory. Querying an uninitialized collection remains supported through source evaluation and does not implicitly initialize it.

Cache dependency verification additionally requires lockfile-read authority, including absence. A query without that grant retains the existing authorized source-only path without invoking cache manifest capture or probing the lockfile. The manifest/recheck guarantees below describe cache-eligible preparation; caching does not broaden the source-only read grant.

The public query workflow holds its cooperating read guard while capturing visible record manifests, preparing cached or source-derived records, and executing the query. Manifest capture authorizes controls before discovery and record contents before opening files, then hashes UTF-8 bytes and obtains metadata from the same secure regular-file descriptor. It rechecks visible membership and controls. Preparation verifies both a second manifest and the actual consumed record revisions/metadata, rejecting observed drift with `stale_state`. Unrestricted readers may populate or repair the disposable record cache; restricted readers only open it read-only and fall back to authorized sources without publishing a partial collection. Unavailable cache storage falls back to canonical sources. This is conservative full-source reconciliation, not an atomic snapshot against external editors, retained generation tracking, or selective indexed query execution.

Control revision capture follows bounded local schema references from type and contract wrappers rather than walking the vault for JSON files. It hashes referenced bytes independently of extension, including malformed schema bytes and explicit absence for missing references; creating or repairing those dependencies invalidates the revision. Wrapper fragment selection and nested-file bases follow the compiler's supported rules. Nonreferenced files outside control namespaces do not invalidate plans merely because they end in `.json`. Existing control-folder membership remains conservatively included. Traversal and file reads are bounded, symlinks fail closed, and this capture does not compile schemas. The permission-aware core capture API requires collection-relative read authority for `mdbase.yaml`, `mdbase.lock.yaml` (even when absent), and complete configured type/contract namespaces before filesystem probes, then authorizes every transitive schema reference before reading or observing absence. Denials are generic and authorized captures preserve the unrestricted digest format. App planning/apply now call this API, including lifecycle recaptures and transaction verification before preflight and after staging. A newly introduced denied dependency aborts before record replacement without disclosing its path or bytes. Trusted unrestricted core wrappers remain available. Dynamic policy support, retained-session invalidation, and the remaining reference-profile audit are still required; filtered capture alone does not satisfy those guarantees.

Registry loads retain fingerprints of the exact config/control/schema bytes actually consumed, including malformed schema bytes and failed/missing reference observations. Repeated conflicting observations and unavailable reads invalidate the evidence; only an observed not-found result proves absence. Contract registries bind the type-registry evidence used for implementations. App preview capture checks this evidence and complete control-file membership against its accepted revisions, so a fresh disk hash cannot certify an older validator. Cache refresh/rebuild performs the same check before derivation and again before publishing rows; stale or mixed registries and control drift preserve the prior cache. Model version 5 rejects older derived rows. Control capture follows the registry's recursive, case-insensitive Markdown discovery even below control folders containing another config file. Verification performs no schema compilation, but still reads controls: this is a correctness boundary, not the zero-I/O warm-session or incremental-refresh performance milestone. External editors can still change disk after the final check; this does not claim filesystem-wide isolation.

Cache model 6 introduced an extension to the model-5 control binding with separately retained authored frontmatter and file metadata. Schema-v21 migration leaves legacy metadata absent rather than synthesizing authored fields from effective defaults; current cache reads and candidate selection reject incomplete payloads until refresh. Rebuild can replace corrupt disposable JSON using source-derived values without changing notes. This adds neither permission authority nor a complete query snapshot: cross-record diagnostics and links require authorized-scope evaluation, and body/exact-source hydration remains separate.

Refresh/rebuild publication also verifies ordinary-record content revisions, file metadata, and current discovered membership against the derived rows. Observed edits, metadata drift, creation, deletion, and rename abort before cache replacement, preserving the prior cache for reconciliation. This is a conservative source-rereading correctness check, not an incremental or zero-I/O freshness mechanism; an external editor can still race after verification. Public indexed-read integration and cooperating generation/lock handling remain open.

Schema v22 retains a separate record-local derivation before collection uniqueness/link/contract overlays. Its nullable migration payload is never synthesized from final cached diagnostics. Reuse requires current source bytes, metadata, model, and control dependencies; CEL inference conservatively rederives. Collection overlays are recomputed, and both local and final rows publish in one transaction after source/control verification. Missing local payloads are rederived; corrupt payloads can be discarded by rebuild without editing notes. This local cache is not a permission-scoped query result or authority proof. Public query reuse is integrated as described above; full dependency-incremental overlays, selective hydration, and freshness/session integration remain open.

The core cached-record-set loader accepts an explicit expected revision/metadata manifest whose completeness and freshness must be proved by its caller under the cooperating read guard. It verifies control authority and snapshots, reads local payloads in one SQLite transaction, and checks record permission before fetching or decoding each payload. It recomputes uniqueness, links, and contracts over visible records instead of copying final cached diagnostics. Missing/mismatched rows and dynamic CEL membership return a cache miss; authorized malformed payloads error, while denied payloads are not inspected. It reads controls but no record sources and cannot detect records omitted from the manifest. The public query caller supplies source-generation verification as described above; the helper itself does not prove it or implement selective body hydration.

Plans are immutable, caller/instance/operation-bound, expiring artifacts outside `cache.db`. A plan records exact before/after bytes, changed paths, creation absence preconditions, accepted source revisions, collection root identity, config/type/contract/schema digests, relevant directory membership fingerprints (including uniqueness and inbound-link candidate sets), permission/config revisions, validation policy version, and all generated lifecycle values. Record revisions are opaque content-derived values. Control edits, new relevant records, deletes, renames, changed grants, or collection rebinding invalidate affected plans.

Resolve `now`, `today`, UUID/ULID, and other generated values once while planning. Apply persists those exact reviewed values; it never silently regenerates them. Plan expiry forces a new preview. Validation and membership are computed against the whole proposed final record set, including intra-batch uniqueness and exactly one post-lifecycle membership check. No provider, script, or plugin performs I/O during planning. Pure supported lifecycle providers run in core; reusable persistence orchestration stays in app.

The core provider evaluator uses the supplied operation clock: `now` emits UTC RFC 3339 with millisecond precision, and `today` uses the collection's IANA timezone. UUIDs are random version 4; ULIDs combine the clock's Unix milliseconds with 80 supplied random bits. The planner must supply fresh entropy per generated ID assignment and retain the result. `copy` preserves JSON types, including explicit null, using the ordinary dotted/JSON-pointer field resolver; missing or multiple source values fail with `lifecycle_provider_error`. `slugify` requires a string, lowercases Unicode letters/numbers, collapses other runs to hyphens, and trims boundary hyphens (an empty result remains an empty string for subsequent schema validation). `literal` preserves its JSON value without interpreting nested provider-shaped objects. These are bounded Vulcan provider semantics; the evaluator alone does not enable lifecycle writes or establish a profile claim.

Core create/update action evaluation uses one pre-lifecycle raw draft snapshot for guards and field providers. Schema-known missing fields bind as null with separate presence information; read defaults are not injected. `old` is the previous raw frontmatter on update and null on create, while reserved `file` and `operation` bindings cannot be shadowed by frontmatter. False/null guards skip the assignment, and compile, runtime, or non-boolean/non-null guard results fail with `lifecycle_expression_error`. A distinct guard is compiled/evaluated once per record evaluation. Within a field's declared action sequence, the last active assignment wins. Identical declarations across matched types are coalesced by type composition; conflicting declarations fail before generation with type names and lifecycle source locations. The evaluator returns an assignment set only on success; the write planner still owns applying it, the single membership recheck, validation, and persistence.

The core draft preparer applies assignments to a copy of raw frontmatter, performs one membership recheck (comparing normalized type sets), and validates schemas only after lifecycle. It rejects malformed input even with schema validation disabled. Target selectors support nested objects, non-root JSON Pointers, and legacy `[]` expansion over existing arrays; they never replace an intervening scalar or append out-of-range array entries implicitly. Missing object parents may be created. Conflicting aliases and parent/child targets fail before returning a changed draft, and expansion is bounded to 10,000 targets with at most 64 selector components. Empty expansions are errors. A semantic no-op preserves exact supplied source, including comments and quoting. When lifecycle changes persisted values, frontmatter may be serialized while body bytes, the initial BOM, and the source's first-line newline convention are preserved. The App planner invokes this preparer before proposed-final-set collection validation.

An apply request includes plan ID, accepted revision set, and idempotency key. The durable operation identity binds key to caller, instance, plan digest, and exact input. Repeating the same apply returns its recorded outcome; reusing a key with different input fails. Direct single-record upstream `if_revision` operations can plan/apply internally under the same lock while retaining the upstream `concurrent_modification` envelope. App preview drift maps to `stale_state`. Never replace existing Vulcan/upstream wire envelopes globally.

The shared App planner derives old/proposed memberships from exact affected sources at a fixed operation clock, authorizes the resulting constraint scope, prepares lifecycle-aware drafts, and validates its whole proposed final snapshot before returning a plan. Candidate sources must match accepted revisions; control, source, or relevant namespace drift across preview captures fails closed. Guards that call `asFile()` require complete collection visibility independently of branch outcomes; string literals do not expand scope. Guards receive pre-lifecycle proposed records and authorized existing-file metadata. Each record's `operation.kind` is `create` or `update`, with the enclosing operation in `operation.parent_kind`. Generated values are retained by path and target selector; App callers cannot inject them. Apply and idempotent replay use the exact planned source without invoking providers.

Generic managed edits use this same preparation and validation. Standalone script mutation results and App note reports reflect final policy-adjusted source; values returned inside an explicit transaction callback remain provisional until commit, so scripts must reread afterward to obtain generated fields. Rename preserves record identity without invoking create/update policies; declared optional `on_rename`/`on_delete` hooks currently fail explicitly with `lifecycle_event_unsupported`. Explicit raw repair skips lifecycle and retains diagnostics without silently falling back from a failed validated write. Complete control-dependency authorization remains integration work; this boundary alone does not advertise record-write or lifecycle feature support.

Current record model 7 adds required body link/tag parse facts to the private local-cache payload. These facts contain no resolved targets or permission-sensitive diagnostics. Cached overlays reuse parsing but resolve links and recompute constraints over the current readable records. The same source-revision, metadata, control, and model checks govern reuse; old model rows rederive, and malformed or missing required facts cannot be treated as empty results. Canonical record envelopes and schema-v22 table layout are unchanged. This does not establish metadata-only hydration, retained freshness, or performance acceptance.

## 4. Batch and rename transaction boundary

`vulcan.record_write.v1` batches and rename-with-reference-rewrites are all-or-nothing for cooperating Vulcan readers, mutations, scans, and managed sync. Version 1 has no best-effort batch mode. Reject plans over 1,000 changed files or 64 MiB combined before/after bytes with `limit_exceeded`; never split an accepted batch into unreviewed commits.

All cooperating entrypoints acquire the same cross-process vault lock. Before making file changes, persist a bounded journal with transaction ID, exact before/after artifacts, preconditions, and recovery phase outside the cache; fsync required files/directories according to the supported platform's durability contract. Securely stage all replacement files on the destination filesystem, revalidate dependencies, then begin the serialized apply. Missing parent directories and case-only renames are explicit planned operations. Never overwrite a newly appeared file, follow an app-controlled symlink, or rewrite an unplanned reference.

A crash before the durable commit decision rolls back staged/applied paths; after that decision recovery completes the committed state and repairs cache projections. Recovery compares observed bytes to the journal's expected before/after bytes. Unexpected externally edited bytes are preserved with both journal versions and block further affected operations for explicit repair, never overwritten by automatic rollback. Reads/scans/sync must recover or report the blocked transaction before exposing a mixed logical result. Emit one committed logical transaction with per-path events only after reconciliation. Delivery/outbox state and idempotency receipts survive cache rebuild. Both are bounded host operational state. Committed outbox events are retained for 7 days and at most 1,000 events, and no production consumer reads them yet. Idempotency receipts are retained for 30 days and at most 10,000. Pruning runs under the write lock after a commit; receipt pruning runs at most hourly, and a housekeeping failure never fails the committed write. Within the receipt window, repeating an apply returns its recorded outcome. After expiry, the same apply is re-checked against its accepted revisions and fails with `stale_state` instead of writing twice. Reusing an expired key with different input is then no longer detected as a conflict. Post hooks and opt-in Git commit run after canonical commit; their failure reports committed-with-follow-up-failure and cannot turn a successful write into a retryable duplicate.

Ordinary filesystem tools and external editors do not honor Vulcan's lock and can observe intermediate path replacements. Do not claim filesystem-wide atomic rename or isolation against direct filesystem control. Recheck external drift before each replacement, preserve evidence on conflict, and document this boundary in CLI/UI previews. Fault-injection tests cover each journal/replace/commit/cache/outbox boundary, concurrent creators, phantom uniqueness records, case-only rename, denied inbound links, and externally edited files during recovery.

## 5. Schema discovery and editable projections

Expose collection/type/contract/schema/view metadata through shared core/app services, then the App API. Collection discovery returns only bound visible roots; it never scans arbitrary host directories. A schema report returns source revisions, effective matched composition, persisted-required rules, effective defaults, editable/read-only fields, conflicts, and required features. Filter source controls and projected contract fields before returning metadata. If the caller cannot read a necessary control, mark the dependent operation unavailable without exposing its content; do not fabricate a less restrictive schema.

Studio patches persisted frontmatter only. Missing, null, empty values, and effective defaults stay distinct; leaving a default untouched does not persist it. Rename and imports use the same planner. Unsupported schemas stay readable with diagnostics. Tests include control-only changes invalidating an open form, newly introduced matching types, hidden linked targets, scope-wide uniqueness authorization, body/comment/quoting preservation, and cache rebuild parity.

## 6. Handoff evidence

Before marking a slice complete, add unit/fixture/conformance tests, direct-mode and restricted-grant tests, failure recovery tests where it mutates files, generated CLI/API documentation, and the bundled-skill impact review. Do not teach installed skills unimplemented commands. Watchers are repair hints: control changes invalidate all affected projections, and notifications wait until a coherent read state exists. No loading or synchronization of a provider/workflow/type-pack record executes code.

## 7. Derived state and Git ignore convention

`.mdbase/` is reserved for derived implementation state and excluded from mdbase record discovery. When a Vulcan workflow or maintenance script creates this directory, it must also create `.mdbase/.gitignore`, if absent, with exactly these contents followed by a newline:

```gitignore
*
```

Preserve an existing `.mdbase/.gitignore` without overwriting or extending its rules. The default ignores itself as well as the directory's other untracked contents; each local creator supplies it rather than relying on Git to distribute it. Do not modify the vault-root `.gitignore` for this default. Ignore rules do not untrack files already committed to Git.

Keep canonical collection files such as `mdbase.yaml`, `mdbase.lock.yaml`, and configured type/contract folders eligible for version control. Required recovery backups and durable reconciliation state belong outside this disposable directory; a backup copy inside it must not be the only preserved original.

This is a Vulcan creation convention, not an upstream requirement for the directory's internal layout. Vulcan currently does not create `.mdbase/` in its mdbase commands. Do not add implicit writes to collection discovery or read-only commands solely to install the ignore file. When a creation workflow is implemented, test default creation, preservation of existing rules, Git exclusion, and unchanged read-only behavior.
