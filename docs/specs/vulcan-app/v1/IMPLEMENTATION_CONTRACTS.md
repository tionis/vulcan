# Vulcan App v1 implementation contracts

Status: normative companion to `SPEC.md`, reviewed 2026-09-07. These decisions close pre-release design gaps; implementation gates and runtime conformance remain unchecked until implemented. No application receives exceptions to these contracts.

## 1. Signatures and package semantics

`signature.schema.json` defines canonical UTF-8 RFC 8785 records under `META-INF/signatures/<key_id>.json`, at most 16 KiB each. Ed25519 public keys and signatures are lowercase hex encoding exactly 32 and 64 bytes. A signature verifies the bytes `UTF8("vulcan-app-signature/v1") || 0x00 || raw_32_byte_AppContentId`. The `app_content_id` field must equal the computed identity. Publisher and key ID must match the manifest-required signer or a locally trusted publisher/key binding to satisfy trust policy; self-reported publisher labels never establish identity. A cryptographically valid unknown signer is untrusted evidence, not a reason to grant or silently reject otherwise inspectable content. Reject malformed or invalid supplied signatures, duplicate key IDs, filename/record mismatches, or missing required signers.

`signature_policy.required_signers` binds publisher, key ID, and full public key into the canonical manifest, avoiding a signature/digest cycle. All listed signers are required, not a threshold. Omission is equivalent in policy to an empty list but retains its distinct content identity. Removing a required record invalidates that blob. Removing/changing the policy changes `AppContentId` and requires new local trust; publisher continuity never follows display version alone. Local policy may require additional trusted signatures and cannot be weakened by a package. Unsigned packages require explicit local trust. Revocation is device policy checked at activation/invocation, not merely at installation.

A detached signer key ID is package-local; local trust indexes the complete publisher/public-key binding, so reusing a display key ID cannot replace a trusted key.

The signed-store fixture includes an intentionally public test key, a signature record, migration assets, and exact content/payload identities. Tests verify signatures and reject content tampering. Gate A additionally builds strict ZIP/blob vectors and hostile byte-level fixtures; these source fixtures do not implement the production validator.

Cross-reference validation resolves all declarations before activation. Function paths have a runtime-compatible media type, views are HTML, schemas are `application/schema+json`, SQL migrations are `application/sql`, and signatures cannot be referenced as payloads. Reject unsupported SemVer/SPDX syntax, duplicate IDs, dangling references, invalid defaults, inconsistent store profiles, out-of-range safe integers, noncanonical arrays, migration cycles/gaps, invalid capability dimensions, or store requirements on non-mdbase stores. The minimal source JSON is authoring input; `apps pack` canonicalizes it. Archive `manifest.json` itself must already be canonical.

## 2. Common API values and authorization

All adapters use the same schemas. API JSON supports null and finite JSON numbers (unlike the manifest's restricted integer-only metadata). Integer-valued JSON numbers must be within ±9,007,199,254,740,991. Exact signed 64-bit values, including ledger amounts and SQL integer cells, use schema-declared canonical decimal strings: `0` or optional minus followed by a nonzero digit and digits, bounded to i64; no plus, leading zero, exponent, or negative zero. SQL values are tagged `null`, `boolean`, `integer` (decimal string), `real` (finite number), `text`, or `blob` (opaque handle). Query/mdbase adapters use schema-tagged exact-number values when the underlying type cannot cross JSON losslessly; ordinary strings remain strings. Clients reject unsafe numeric literals rather than rounding them. Binary inputs use bounded blob handles or schema-declared base64, never an untyped array with ambiguous encoding. Artifact/blob reads and uploads use explicit offsets and at most 1 MiB per call, with expected object digest/size and bounded total quota. A network response larger than the negotiated inline result limit returns a derived or temporary blob handle plus bounded metadata; it never bypasses the 32 MiB invocation result ceiling by embedding a larger body. Only complete size/digest-verified uploads can become mutation inputs.

Each method validates caller/session, installation, instance, entrypoint request, runtime ceiling, and current canonical policy. Existing script/Dataview sandbox tiers remain unchanged; app engines expose only these App API capabilities and never inherit raw I/O merely because a host uses an unrestricted script tier. Installation policy supplies an explicit App API ceiling, default-deny for undeclared operations. Store authority does not replace vault authorization. Private store operations require the corresponding store grant; canonical store operations also require read/write/delete on affected vault artifacts/records. Admin cannot bypass separate deletion or publication grants. `query.run/search/graph` require the corresponding query/search/graph grant and ordinary path-read filtering. Jobs, subscriptions, plans, results, blob handles, and cursors are bound to the same instance and initiating subject/grant; knowing an ID grants nothing. Recheck revocation on each call and immediately before committing side effects.

| Methods | Additional authorization and routing |
| --- | --- |
| `app.*` | Own instance's non-secret metadata; features list only its declared/available features; `log` is redacted, bounded invocation-local structured output |
| `settings.*` | `app.settings.read` for describe/get; read plus `app.settings.write` for plan/apply, intersected by keys/targets and host configuration authority; see `SETTINGS.md` |
| `functions.invoke` | `app.functions.invoke` for a function in the same instance; callee request intersection |
| `runtime.clock/random` | Corresponding resource-free capability; clock returns RFC 3339 UTC and invocation monotonic elapsed time, random accepts 1–4,096 bytes with 64 KiB total per invocation |
| `content.render` | Bounded pure sanitization/rendering of supplied HTML/Markdown or an authorized blob; no implicit vault embeds, file reads, remote fetches, or executable HTML |
| `notes.*`, `tasks.*`, `artifacts.*` | Matching read capability and visible path/media selectors; artifact read returns bounded chunks or a scoped blob handle |
| `mutations.*` | Operation-specific note/task/artifact write or delete; status also verifies plan ownership |
| `stores.mdbase.*` | Store read plus visible collection/control/record reads; query additionally requires `vault.query`; plan additionally requires store write and affected note writes/deletes |
| `sessions.*` | Join for join/heartbeat/snapshot/leave; manage for create and manager transitions; section 6 defines participant commands |
| `jobs.*` | Enqueue/schedule grant for the target function; get/cancel restricted to owned jobs unless an explicit host administrator acts; progress may update only the currently executing host-bound job |
| `events.*` | Subscribe capability; unsubscribe restricted to owned subscription |
| `network.fetch`, `secrets.invoke` | Domain/port grants; secrets additionally require named secret, operation, and host-owned origin-bound adapter |

| `tools.*` | Visible typed tool registry and `tools.call`; no implicit app command registration |

Resource selector dimensions are ANDed, values within one dimension ORed. The literal `*` is valid in resource allowlists but cannot be combined with other values in that dimension. Local declaration/reference ID sets never accept `*`. `secrets.use` requires secret, domain, and operation selectors; it cannot mean arbitrary secret injection into an arbitrary request. Network domain `*` does not bypass DNS/IP checks. Tags/types constrain resolved records; path grants remain required by canonical policy. A record without a requested tag/type does not match.

`functions.invoke` takes function ID, structured input, and common request metadata. It never accepts another instance/package or raw module path. The host checks input/output schemas and intersects callee requests with caller authority. The complete nested call tree shares the outer deadline, cancellation, memory/output/work accounting, and a depth limit of 8 (including nested tools/jobs invoked synchronously); recursion cannot reset budgets. Durable enqueue is a separate approved job, never an escape from the initiating grant. Disabled runtimes return `unsupported_feature` even if a manifest function exists.

## 3. MDB bindings and metadata

An instance binds a declared store to one collection root, optional narrower type/contract/path selectors, and supported feature requirements. Follow `../../mdb/IMPLEMENTATION_CONTRACTS.md` for write guarantees, visibility, upstream draft profiles, and native feature names. `store_requirements` is per entrypoint; unsupported write features do not disable read-only entrypoints.

`stores.mdbase.collections` lists only bound readable collections with supported profiles/features and revisions. `types` and `contracts` return readable definitions and their source/digest revisions. `schema` accepts a record revision or proposed persisted draft and returns effective composition, defaults versus persisted-required fields, editable fields, diagnostics, and dependency revisions. `views` lists named views and optional `.base` source envelopes with revisions when their feature is available. No method exposes private host paths or unreadable controls. `read`/`query` preserve canonical mdbase envelopes inside the App API result. `plan` returns a standard mutation plan; apply/status use `mutations.apply/status`.

The first bound collection is selected by the user/administrator; an app cannot infer ownership from a type name. Bootstrapping `_types/`, `_contracts/`, or `mdbase.yaml` is a separate reviewed control-file plan. Conflicting pre-existing contracts and unknown revisions block bootstrap rather than replacing another app's definitions. Several apps may share a collection without owning its schema migration authority.

The [MDB performance and native integration contract](../../mdb/PERFORMANCE_AND_NATIVE_INTEGRATION.md) defines the first-party App-backend readiness gate: bounded warm metadata queries target p95 below 50 ms and p99 below 100 ms through the local host boundary, with explicit fixture, freshness, and authorization conditions. Apps and standalone scripts share synchronous collection services and mdbase semantics. This adds implementation acceptance criteria, not a new store engine, query dialect, manifest field, or replacement for `stores.mdbase.*`. Write readiness still requires the MDB mutation contract and separately measured write budget; ordinary CLI/script integration does not depend on App packaging or daemon availability.

## 4. Plans, stores, and migration

Canonical mutations, publication, store administration, and migrations use plan/apply. `mutations.plan` accepts versioned typed note/task/artifact/MDB operations and `canonical_sql` requests (bound store, parameterized statements, and dependency revisions), never raw CLI strings or generic host commands. `stores.sql.transact` is only for private stores; canonical SQL uses `mutations.plan/apply/status`. `stores.admin.plan/apply` handles schema installation/migration, reset, archive, and deletion under explicit store-admin plus applicable vault authority. Before enabling an operation, its discriminator and request/report/error fixtures join the generated registry. Plans bind exact source/config/schema/grant/store revisions, generated values, destination absence checks, and caller/instance. Private KV/SQL transactions use expected revision plus idempotency key and execute atomically within one store. Temporary blob puts need an idempotency key but no user preview; canonical blob creation/deletion is staged and committed through a mutation plan. Never infer that a generic `sql.transact` call can write a canonical artifact immediately.

V1 does not offer a transaction spanning private stores, multiple canonical databases, remote processors, and Markdown. Each such workflow journals explicit independently idempotent steps and reports partial/indeterminate outcomes; no success before canonical commit. MDB multi-file batches have their own journal contract. Local database audit rows and ledger postings must share one SQLite transaction. Cross-store account references are immutable reviewed snapshots, revalidated at apply under the vault lock; they are not cross-database foreign keys.

SQL execution uses host-parsed, parameterized single statements under a SQLite authorizer, with DDL allowed only through approved migration plans. Deny transaction-control SQL, ATTACH/DETACH, native extensions, virtual-table modules unless explicitly host-provided, unsafe pragmas, filesystem functions, and reads of host-internal databases. Host quotas include WAL, temporary files, staged captures, backups, output rows/bytes, and execution time. Abort on cancellation before commit; after commit return the durable outcome via status, not a promise that cancellation undid it.

A store's `schema_version` is its exact required version in v1. Its optional `migrations` array contains adjacent ascending SQL transitions (`to_version = from_version + 1`), unique IDs/from versions, inventoried paths, and no gaps from initialization version 0 to the required version. The fixture starts at 0 → 1. Omitting migrations requires a pre-existing compatible SQL schema; host-allocated non-SQL stores start empty and validate against their declared schema. SQL files are parsed as bounded statement lists, never shell scripts or runtime functions; hashes come from `files`. Migration planning runs only on a private disposable snapshot, produces exact schema/data diffs and quota estimates, and performs no external side effects. Apply requires an exact source revision, durable backup, journal, validation, and an explicit approved plan. SQL code cannot reach another store, network, secrets, or vault files. A failure leaves original bytes/schema active; code rollback requires a compatible store version. Downgrades and arbitrary executable migrations are unsupported in v1.

Instance configuration declares a version and JSON Schema; updates supply explicitly reviewed replacement config validated by the new schema. There is no inferred config migration function. Unknown versions block dependent activation. Omitted configuration declaration permits only an empty object. App-wide layered `settings` are a separate declaration governed by `SETTINGS.md`; instance configuration never implicitly overrides them.

For `sqlite-artifact-v1`, the canonical file is a closed, complete single SQLite database with no required external WAL/SHM. Read a verified snapshot; never keep a writable connection to the canonical vault path. A write plan clones the accepted artifact to host-private staging, executes guarded SQL transactionally, checks integrity/foreign keys, closes/checkpoints it, and records exact output bytes. Apply rechecks artifact and referenced Markdown revisions under the common vault lock, then atomically replaces the complete artifact via the shared file journal. Persist the idempotency outcome before exposing success. Sync reads only closed canonical artifacts. An externally edited artifact with unresolved sidecars blocks use; never discard a WAL or checkpoint an untrusted concurrent writer implicitly. Staging/backup files are private, excluded from sync, and recoverable; cross-device conflicts preserve both versions for review.

## 5. Browser bootstrap and asset isolation

The iframe uses `sandbox="allow-scripts"` with no `allow-same-origin`; sandboxed documents therefore have opaque origins, rather than the asset server's origin. This follows the [HTML sandbox definition](https://html.spec.whatwg.org/multipage/iframe-embed-object.html#attr-iframe-sandbox). The host must not authenticate a message merely because its origin serializes as `null`.

A host-owned bootstrap wrapper identifies one validated package/view and one fresh launch nonce. It has the same sandbox/CSP restrictions as the app; wrapper bytes are host transport, not a changed package identity. Do not put credentials or grants in asset URLs. Use `Referrer-Policy: no-referrer`. The parent tracks the exact iframe window and launch generation; the bootstrap transfers one endpoint of a newly created MessageChannel with `vulcan.ready` to the exact parent origin. Parent checks source, opaque origin, nonce, version, and exactly one port, consumes the nonce, then replies only through that port. Child accepts init only on its retained endpoint. No host port is transferred via a wildcard window message, and subsequent window-level messages never gain authority. Load/reload, instance disable, grant revocation, and parent logout revoke the channel. A pending handshake expires after 10 seconds. Test navigation during ready/init, sibling opaque frames, duplicate ports, stale nonce replay, and asset-origin direct visits.

Static assets are immutable inventoried bytes served without credentials; validated package assets must be considered readable to users who receive the package. Authorization protects vault/private data, not secrecy of JavaScript source. Host-derived CSP permits the exact asset namespace and hash-approved bootstrap, denies `connect-src`, `frame-src`, `object-src`, `base-uri`, `form-action`, workers and top navigation, and restricts `frame-ancestors` to the configured WebUI origin. Styles/scripts must be bundled; inline assets require host-derived hashes. Opaque-origin ESM/font requests use credentialless asset-only CORS; never enable CORS for a daemon API merely to make modules load. Deployments unable to isolate asset serving from the WebUI origin report unsupported hosting. Same-frame navigation can happen; sandbox/CSP are not a browser-wide egress firewall. Strong prevention of all browser exfiltration requires a separate browser/network-isolation profile and is not promised by v1.

## 6. Live sessions, events, jobs, and processors

Live sessions require a daemon. `sessions.create` requires manage, names a bound live store and initial schema-valid state, and returns an opaque session ID. Join authority alone cannot change shared state. The host assigns participant identity from the initiating subject/session, validates heartbeat/expiry, and exposes only visible session data. Snapshots carry expected sequence and state revision. `sessions.command` uses that sequence plus idempotency and invokes the store's declared `command_function` when present. The reducer receives a host-authenticated role/participant identity, command, and current state; it is pure computation without host I/O and returns proposed state/events. State has a host-owned envelope `{shared, participants}`: `shared` is app-schema-validated JSON, and `participants` maps host-issued participant IDs to bounded per-participant app-schema-validated JSON. Membership, roles, sequence, and expiry are host metadata outside that writable envelope. The host applies schema, participant/manager policy, size, and revision checks before commit. Participant commands may only change their own queue/hand/presence entry; manager commands may change shared lifecycle/current-item/timer/queue state. A reducer cannot invent a participant or promote roles. Without a reducer only host heartbeat/join/leave is supported; Gate D tests the substrate and Gate E enables app reducers.

Meeting decisions/actions/finish first apply the canonical note plan idempotently, then advance live state with the resulting note revision. Journal that boundary so reconnect/retry can reconcile an already committed note change; session expiry never deletes canonical content. Finishing always transitions active or paused to finished. Checkpoints are host-owned durable operational recovery state, with a separately reviewed retention setting; they are not a relabeling of temporary presence into canonical wiki data.

Events are at-least-once after coherent reads, with stable source event IDs and per-subscription delivery sequence. Filters/queues are bounded. Origin/causal chains suppress direct self-retriggers by default; a handler cannot turn a derived output event into an unbounded ancestor loop. `event_handlers` use this fixed v1 policy; no undeclared loop-policy field is inferred. Overflow forces resnapshot. Exactly-once remote side effects are not promised.

Jobs persist the package digest and an access-controlled replay-input reference separately from redacted logs. Retry resolves current secret bindings and rechecks grant, schema, deadlines, retry count, and idempotency. Expired browser authority cannot survive restart unless the user explicitly established an attenuated service grant. Disable blocks new claims; cancellation before a remote request prevents it, while unknown remote completion is recorded as a `blocked` job with `unavailable` error and `indeterminate` detail; it requires status reconciliation before retry, never an invented success or an automatic duplicate submission.

Processor bindings are host-configured typed adapters, with operation capabilities, reviewed endpoint or executable ID, and finite request/report contracts. `processors.plan` produces a source/recipe/output-bound operation plan; `submit` requires that plan and idempotency; status/cancel/fetch verify ownership and current grants. `validate` is bounded pure artifact validation and returns an import preview, never an implicit canonical write. Network adapters obey domain/redirect/secret policies; host execution uses a preconfigured typed adapter, never arbitrary argv or shell. Blobforge's pinned protocol/fake coordinator is required before enabling its adapter; adding provider-specific operations requires explicit typed registry review.

## 7. CLI parsing and handoff tests

Commands are flat manifest IDs; examples such as `bulk plan|apply` use a declared `bulk` command and validated action positional, not implicit nested CLI injection. Input is one object keyed by declared positional/option `name`, plus reserved `stdin` if requested. Names/long/short flags must be unique; forbid collisions with host `--output`, `--dry-run`, `--help` and reserved `stdin`. Only the last positional can repeat, and required positionals cannot follow optional ones. Repeated values become ordered arrays, absent optional values are omitted unless a validated scalar option default exists. Boolean options accept presence as true and explicit true/false values. Integers parse without float conversion; values outside JSON-safe range use a declared string schema instead. Text/JSON stdin is bounded UTF-8; bytes become a bounded invocation blob handle. Output is a schema-validated value rendered by Vulcan; never arbitrary stdout.

Mutating app commands receive host dry-run intent in context. During dry run the host denies apply/transaction/enqueue/network/processor-submit/secret operations; only reads, pure calculation, and side-effect-free plans are available. `--dry-run` must return a plan or explicit unsupported diagnostic, never silently execute the function's effects. Canonical apply consumes a reviewed plan ID; arbitrary custom code does not become safe just because `mutating` was declared false.

Before handoff implementation, use the roadmap gates and the per-example matrix rather than interpreting all v1 methods as Gate C dependencies. Before each gate ships, check domain/request/success/error fixtures, authorization mapping, schema projection parity, malformed inputs, denied/revoked authority, stale plans, concurrency, interruption and recovery. Planning tests validate schemas, signature vectors, and declared combinations; runtime/browser and MDB atomicity tests remain required implementation work. Review bundled skills when those commands ship, not by advertising roadmap features early.

The Gate A handoff includes a method-to-gate implementation ledger with typed operation discriminators; this is a required implementation artifact, not permission to add undocumented methods. A missing mapping or schema blocks that method, while a disabled optional method returns a stable feature diagnostic.
