## Daemon runtime, services, packaging, and companion transports

- The daemon sync supervisor is transport-independent and persists a versioned, bounded job ledger below the platform Vulcan state directory using atomic replacement. It coalesces duplicate queued triggers per wiki, creates at most one follow-up when events arrive during a running job, prevents two claimed mutations for the same wiki while allowing different repositories to progress concurrently, and exposes cloneable cooperative cancellation to the finite application workflow. Registered wiki, group, and all-wiki requests create a durable aggregate parent around normalized per-wiki children; parent state is derived from independent child outcomes and never claims a cross-repository transaction. Credential-scoped replay survives restart. Cancelling one aggregate preserves a coalesced child still referenced by another active aggregate and otherwise delegates to normal queued or cooperative child cancellation. A restart converts interrupted running jobs back to queued recovery work; Git-reachable snapshots and the application journal remain the authoritative byte-recovery boundary.
- `vulcan daemon start` makes those library boundaries deployable without a second binary. One device-local process lock prevents duplicate runtimes; the process binds the configured loopback address before atomically publishing a bounded runtime record, loads the device companion credential, starts the registry-driven watcher/periodic-trigger coordinator and retained-job worker, and serves the companion router. Foreground Ctrl-C, service-manager termination, and authenticated `POST /shutdown` first enqueue a retained final sync for every active Git-backed wiki, allow up to 30 seconds for those jobs, cooperatively cancel unfinished work at the deadline, and only then set the stop flag; the listener, worker, and every watcher join before the owned runtime record is removed. A suspend-sized wall/monotonic clock gap adds a resume reconciliation immediately after wake on platforms that cannot provide a reliable pre-sleep event. `daemon status` authenticates a capability probe instead of trusting a stale PID file; a missing runtime is stopped, while existing runtime metadata whose probe fails is explicitly unresponsive rather than falsely labeled stopped. `--detach` re-executes the same binary with inherited device configuration and redirects output to the state-directory log. Quiet daemons emit structured, deduplicated, secret-minimal warning/error records when a job is conflicted, paused, or failed (wiki, job identity, category, retryability, and retained-status guidance), plus the existing specific checked-out-branch failures; full error text stays on authenticated status surfaces, while `--verbose` adds every completed-job summary. Native desktop delivery is an opt-in consumer of the same attention event. A device-local policy can ignore network failures or delay a single native alert until a failed-job count or observed duration; operational logs and remote sinks retain their independent event policy. Native notices identify the wiki, category, retryability, and job, while full error text stays on authenticated status. It runs on a bounded background queue, invokes the platform helper without a shell, times the helper out, and reports delivery failure without delaying or rewriting synchronization results. Remote JSON webhooks, ntfy publishing, and local command adapters consume the same versioned event through a bounded device-state ledger: the daemon persists intended targets before dispatch, reconciles retained terminal jobs at startup, uses stable job identities for receiver idempotency, retries with bounded exponential backoff, and retains completed records to suppress replay. HTTP follows no redirects, accepts only HTTPS or loopback HTTP, and reads optional bearer values from named environment variables; local adapters receive JSON on stdin through an absolute executable without a shell. Every delivery re-applies the affected wiki's network or execute permission. Sink failure is visible through rate-limited warning logs and `daemon alert-status` but never changes sync state. `daemon config show/set-bind/set-agent/clear-agent/set-notifications/set-notification-webhook/set-notification-command/remove-notification-sink` atomically manages non-secret device configuration with dry-run previews: agent entries contain only a validated OpenAI-compatible base URL, explicit model, and optional environment-variable name. Startup resolves named secret environment variables into memory and never persists or reports credential values. None of this changes direct CLI behavior.
- `vulcan daemon install/uninstall` projects that same foreground process into a native per-user service without introducing a second lifecycle implementation. Linux uses an atomically replaced `systemd --user` unit with restart-on-failure, Windows uses an XML-defined Task Scheduler logon task whose trigger and interactive-token least-privilege principal are both bound to the current user SID, and macOS uses a per-user LaunchAgent managed through explicit `launchctl` argument vectors. Windows task names include that SID so registrations from different users cannot collide, and installation does not require elevation or a stored password. The Windows task invokes the existing detached-start path, and installation explicitly runs the registered task rather than waiting for the next logon. The one supported Windows binary remains a console-subsystem executable but embeds Windows 11 24H2's `consoleAllocationPolicy=detached` application manifest, preserving normal output and blocking inside an existing terminal while preventing Task Scheduler from allocating even a transient console; no helper executable is required. Planning is explicit and mutation-free under `--dry-run`, service definitions contain no secret values, symlinked definitions fail closed, and uninstall preserves all Vulcan registry, credential, journal, conflict, and vault state. A permission-checked device-local `daemon.env` is resolved by a platform-neutral startup path where the service manager cannot safely provide an environment file; generated plists or task definitions never embed expanded credentials.
- Android defaults to finite wake-driven execution rather than a resident daemon. `sync termux-install` projects the ordinary registered-wiki `sync run` command into a private Termux wrapper managed by Android JobScheduler. The adapter requires the detached `android_shared` layout, respects Android network, battery-not-low, storage-not-low, optional charging, and reboot-persistence constraints, and uses the platform's 15-minute minimum period. Its stable per-wiki job and device-local bounded manifest are packaging state, not synchronization authority. A Termux shortcut, Obsidian resume/save bridge, or future native WorkManager client may invoke the identical finite command for lower latency; the scheduled job is a coalescible safety net and no Android-specific merge path exists.
- Distribution is archive-first and forge-neutral. Versioned per-target Linux, Windows, and macOS archives plus a distinct full-feature aarch64 Android/Bionic archive, deterministic amd64/arm64 Debian packages, checksums, and a machine-readable artifact manifest form the canonical release contract; installer scripts and package-manager definitions project the same binaries and generated assets rather than rebuilding Vulcan's configuration or service semantics. The Android build retains the ordinary CLI feature set, generates QuickJS bindings against the matching NDK sysroot through `bindgen`, and disables LLVM's SLP vectorizer to avoid the verified AArch64 release-optimization compiler crash. The POSIX installer selects the Android artifact only in Termux and must never relabel a GNU/Linux arm64 binary as Android-compatible. The signed-envelope update-channel contract defines `stable` and opt-in rolling `main` streams independently of any forge or registry; the latter is published under a distinct `rolling-main` channel tag that is created once and never moved, with only its release assets replaced in place, so it neither collides with the source branch nor requires a forced tag update. Portable manual installs may verify and atomically replace themselves through the shared application updater, while package-managed installs remain owned by their package manager. Signature requirements, trusted keys, and downgrade policy are local and cannot be weakened by remote metadata. Portable installations may opt into a device-local unattended schedule: Linux uses paired `systemd --user` oneshot/timer units, macOS uses a calendar-triggered per-user LaunchAgent, Windows uses a SID-scoped daily Task Scheduler definition, and Android/Termux uses a persisted periodic JobScheduler wrapper because Android cannot guarantee an exact wall-clock execution time. Scheduler definitions contain only the absolute executable and non-secret channel and condition options, invoke one vault-independent update cycle, and cannot enable unsigned metadata. A cycle downloads and verifies the complete candidate before interacting with the daemon, refuses an unresponsive runtime, gracefully stops a live daemon for the shortest replacement window, and restores its installed native service or detached lifecycle after either success or replacement failure. Optional failure delivery invokes the platform notification helper without a shell and never changes update results. Installation never registers a wiki or enables the daemon implicitly, and removal preserves device and vault state. Homebrew may expose its own explicit service integration using a stable package path, while the built-in service installer remains available for direct archives and Debian installations. Git stays an explicit package/runtime dependency for the initial synchronization backend, and Android remains subject to its separate real-device certification gate.
- Unattended work uses a reusable application-layer network and power policy with explicit unknown-state behavior. New portable self-update schedules default to unmetered network and battery-not-low, checks conditions before its metadata request and again before an archive download, and reports deferred cycles without treating them as failures. Android/Termux projects supported network, battery, and charging constraints into JobScheduler; Windows projects the optional charging requirement into Task Scheduler. Runtime probes use the active NetworkManager metering state and Linux battery data, plus bounded macOS and Windows battery readings, where available. Unsupported or unavailable readings remain unknown, rather than being inferred from an interface type; the default permits them to avoid indefinitely starving scheduled updates. Automatic sync can reuse the policy with its own defaults without changing manual sync semantics.
- A claimed daemon job invokes `vulcan-app`'s finite transaction rather than a daemon-specific Git path. The app observer persists its journal/apply marker first and only then forwards each phase to the supervisor's retained `SyncStatus`; registration identity, path, backend, pause state, and named permission profile are revalidated immediately before execution. Automatic triggers stop at a paused registration without discovering Git, while explicit manual jobs retain direct-mode semantics. Terminal success, conflict, pause, cancellation, or typed failure is atomically retained with the job and can be projected by later CLI or companion transports. Engine classifications such as network, busy, repository, configuration, and invariant cross the application boundary as structured data; the daemon must not flatten them into retryable `unknown` errors, because offline projection and repair guidance depend on category and retryability. A checked-out branch pull or publication failure does not reverse an already converged hidden file lane, but the encompassing daemon job is still retained as failed with `error` status and detail naming that partial-success boundary; aggregate and companion surfaces must not report the operation as wholly successful.
- Daemon status is reconstructed rather than maintained as a second authority. The shared state contract distinguishes clean, dirty, capture-pending, capturing, captured-unpushed, fetching, fetched, merging, pushing, applying, conflicted, paused, offline, and error. Reconstruction prioritizes an active retained job, then an application marker and durable transaction journal, unresolved conflict records, registration pause state, and finally the latest terminal job. Retryable network/authentication failures project as offline, watcher work waiting in the queue projects as dirty, and journal phases retain transaction identity plus whether recovery is required. A retained journal error overrides its last active phase in the projected state, so a failed merge or apply is never displayed indefinitely as running. `daemon status` performs this reconstruction read-only for every registration, reports the latest daemon-supervised attempt time from the retained job identity, and reports whether a notification advertisement is present in the local cached discovery ref. It does not fetch a remote merely to produce status, does not expose the capability URL, and distinguishes never-attempted, not-yet-discovered, disabled, and unavailable states. Direct one-shot `sync run` invocations are outside the daemon job ledger. None of this state is inferred from `cache.db`.
- Each registered Git worktree has a daemon-owned recursive watcher that schedules the same finite transaction rather than scanning the cache directly. It coalesces editor save sequences after a short quiet period but caps continuous activity with a maximum dirty age. Access events and `.git`/`.vulcan` paths are ignored; transient notify errors confined to ignored device-local state are discarded. Failed setup or a runtime native-watcher failure falls back to content-comparing polling, while a bounded incremental safety rescan detects a native watcher that remains connected but silently misses an edit. Watcher rescan notices, callback errors, and unreadable apply markers force a recovery trigger. Events observed while `vulcan-sync/apply.json` is present retain that transaction ID in bounded job metadata instead of being blindly discarded, because a simultaneous user edit must still produce a follow-up reconciliation. Startup schedules an idempotent resume or recovery job before consuming events; periodic remote polling remains a separate trigger producer over the same supervisor.
- A synchronous trigger-runtime coordinator projects the current registry into watcher ownership. An active, unpaused Git registration owns exactly one watcher; removal, pause, or a watcher-relevant identity/path/backend change stops and joins it, while resume starts a fresh watcher and therefore a startup reconciliation. Watcher failure is retained as recovery metadata and retried on a later registry pass. A separate monotonic periodic timer enqueues `Poll` jobs for the same active set, so local events, startup, remote polling, and future notifications all converge on the supervisor's per-wiki serialization and coalescing rules. Runtime exit and coordinator errors stop and join all child watchers.
- Remote Git wakeups use the minimal HTTPS long-poll contract in `docs/specs/realtime-sync-notifications.md`, not the loopback companion protocol and not a Vulcan-specific relay. Each registered Git wiki discovers its own endpoint from `refs/vulcan/notifications`; the fetched Git object is the durable device-local configuration, so Vulcan does not import or duplicate a subscription bundle or credential. The daemon owns one interruptible listener per advertised wiki, applies the wiki's network permission profile, bounds reconnect behavior, and turns any successful response into `SyncJobTrigger::RemoteNotification`. The response body cannot select a repository, ref, local path, or Git object and is ignored. Notifications cannot resolve conflicts or replace startup and periodic reconciliation.
- Companion transports project a versioned synchronous service rather than calling Git directly. The service owns capability negotiation, wiki lookup, reconstructed status, credential-scoped idempotent single-wiki and aggregate selection enqueueing, pause/resume, conflict inspection and deterministic resolution, optional agent proposal creation plus explicit proposal approval/rejection, deterministic or agent-backed semantic-plan creation, and child/aggregate job status and cancellation. Repository-reading and mutating calls reapply the registration's named permission profile. Resolution and semantic providers, endpoints, models, and credentials are configured server-side rather than accepted from a companion request; each provider reports its actual network endpoint for permission checks, and each agent capability is advertised only while the corresponding provider is configured. A configured daemon claims each repository/conflict pair before calling the resolution provider, permits one active proposal request for that pair, fails concurrent requests immediately, and releases the claim through scoped cleanup; capability negotiation reports both the limit and its `daemon_process` scope so clients do not mistake this device-local guard for cross-device coordination. Semantic planning continues to accept deterministic requests without a provider, fails an explicit agent request closed when none exists, and reuses the same bounded-patch, exact accepted-tree, review, and application contract as direct mode. HTTP and WebSocket adapters add their transport capabilities without duplicating these workflows.
- Companion authentication uses a device-local credential outside every vault and rebuildable cache. The initial credential contains a 256-bit OS-random URL-safe bearer secret, a stable non-secret credential ID used to scope idempotency records, and a bounded exact Origin allowlist. Creation is atomic and no-clobber; token comparison is constant-time and debug output is redacted. Unix loads reject group/other-readable files, while Windows relies on the inherited ACL of the per-user state directory. Browser WebSocket clients authenticate with a bearer-bearing subprotocol because the standard WebSocket constructor cannot set an `Authorization` header; HTTP requests continue to use the header.
- The reference Obsidian companion is a thin protocol client, not another Git owner. Its distributable `main.js` is bundled from the dependency-light source under `integrations/obsidian-vulcan` for desktop and mobile, and the release assets are also embedded into Vulcan for `vulcan daemon companion install [<wiki>] [--dry-run]`. Installation is limited to registered vaults with a real `.obsidian` directory, updates only managed assets, preserves existing plugin data, and seeds the non-secret loopback endpoint and wiki ID only on first install. Non-secret loopback endpoint, registered wiki ID, debounce, event, and failed-sync-notice preferences may use ordinary plugin data; the bearer secret requires Obsidian 1.11.4+ `SecretStorage` and is never passed through `saveData` or written by the installer. Manual sync first requests Obsidian's editor-save command and then enqueues the ordinary daemon job. Optional save triggering starts only after completed vault `modify` events, is debounced, and refuses to enqueue while reconstructed state is busy, paused, or conflicted. Status bar and WebSocket snapshots expose the daemon's state; by default the authenticated stream and 30-second polling fallback also produce one bounded Obsidian notice per durable failed job or retained failed transaction, deduplicated by its identity. Temporary companion connection loss changes status to offline but is not reported as a sync failure. Preserved-side conflict resolution always performs a mutation-free preview and requires a separate explicit apply action that reuses server-side stale, recovery, lease, validation, and application checks. The client validates loopback origins and protocol payloads, sends credentials only in authorization/subprotocol fields, and contains no Git execution path.
- The initial companion transport refuses non-loopback listeners. HTTP operations use JSON, `Authorization: Bearer`, `Vulcan-Protocol-Version: 1`, exact Origin checks when the header is present, and authenticated CORS behavior; manual sync, aggregate selection sync, and resume additionally require `Idempotency-Key` and return HTTP 202 with the retained job report. `POST /sync` accepts exactly one of `wiki`, `group`, or `all`, while `/aggregate-jobs/{job}` monitors or cancels the parent and ordinary `/jobs/{job}` continues to expose each child. WebSocket upgrades negotiate `vulcan.v1` and authenticate a second `vulcan.bearer.<token>` subprotocol, avoiding URL credentials and browser-inaccessible custom headers. The bounded event loop sends an initial snapshot and then only changed snapshots of registrations, reconstructed per-wiki status, retained child jobs, and retained aggregate jobs. Synchronous app/registry/supervisor work runs behind the async boundary with `spawn_blocking`.
  The concrete v1 wire contract is documented in `docs/companion_protocol.md`.

## Git engine, ref namespace, and device safety state

- `vulcan-sync` owns synchronous device/file-tree backend contracts and typed repository-engine operations. Its versioned, serializable plan/report/status/conflict/job/error schemas and explicit capability declarations are shared by direct, daemon, companion, test, and JSON surfaces; the finite `SyncBackend::sync_once` contract deliberately excludes scheduling and retained lifecycle state. Its initial `GitCliEngine` uses fixed Git CLI operations and reports installation plus colocated, detached, and bare repository layouts, while `GitSyncBackend` adapts the implemented finite Git cycle to the backend-neutral contracts without overstating conflict preservation. Every engine command uses one captured-I/O spawn boundary: Unix starts a process group for bounded timeout cleanup, and Windows applies `CREATE_NO_WINDOW` so background daemon cycles and Git-spawned helpers cannot flash console windows. Daemon scheduling and complete vault transactions stay outside this crate. Finite cycles expose typed progress observations and a cloneable cancellation token, checking cancellation only between safe Git operations after preserving any captured candidate.
- Agent-facing Git synchronization remains narrower than the human CLI and companion transaction surface. The MCP `sync` pack contains only mutation-free status, finite-cycle preview, doctor, and immutable conflict list/detail tools with closed JSON schemas; it never exposes arbitrary Git arguments or conflict resolution. Because these reports can name any path in a repository-wide tree, visibility and execution require both the profile's Git capability and unrestricted vault read access. Profiles with path-filtered reads must use narrower note/query tools instead of receiving a partially redacted sync report that could obscure a safety invariant.
- The Git ref layout is a formal versioned contract owned by `vulcan-sync`, not a collection of call-site strings. Version 1 centralizes validated builders for device-local candidate/fetched/pending refs, epoch archives, conflicts and their recovery/decisions, checkpoints, semantic proposals, detached-loss recovery, and remote per-device safety heads. Sync reports expose `refs.namespace_version`, and created live and epoch commits carry `Vulcan-Ref-Namespace` trailers so recovery tooling can interpret reachable state independently of the rebuildable cache. Local `refs/vulcan/**` are never published. Every mutating finite cycle separately pushes the captured snapshot object to `refs/heads/__vulcan-sync/devices/<profile>/<device-id>` before pull or canonical reconciliation. One moving exact-lease head per device bounds remote-ref growth. A fast-forward retains prior history normally; reuse of one device identity by divergent restored checkouts creates a reproducible two-parent same-tree bridge so neither history is discarded. Current writers emit namespace version 2 while retaining legacy ULID device IDs. A staged recovery reader recognizes canonical key-shaped `vdev1_...` backup heads without changing version-2 legacy-ID writers; key-shaped refs remain untrusted recovery evidence. A later version-3 live reader must preserve the maximum observed namespace version on every new live descendant before key-ID writers activate. Legacy ULID heads remain readable recovery state. Current version-2 readers reject future live-tip versions before canonical reconciliation, after preserving a captured local safety backup. Generic Git transport conformance proves custom refs can use fetch and leased mutation, but the interoperable remote default remains the hidden branch `refs/heads/__vulcan-sync/live` with its epoch and device subtrees until a deployed Forgejo passes explicit permission, advertisement, webhook, maintenance, and Actions checks.
- Friendly device labels are optional, mutable display metadata in shared `.vulcan/device-names/<device-id>.json` files. They travel through ordinary vault sync when tracked by Git, stay outside the rebuildable cache and note frontmatter, and do not affect ref names, identity comparisons, or recovery commands. Unknown devices remain identifiable by their full IDs.
- The read-only device inventory reports remote safety heads, whether each has a matching local recovery ref, retained local recovery refs with no remote head, and names without any backup. A local recovery copy marked current only matches the observed remote revision; it does not establish integration with live or permission to delete the backup. The installation-wide projection keeps local identity and legacy sync actor distinct, groups recovery evidence by registered wiki, and records each wiki's independent remote observation; an unavailable remote does not erase local evidence or imply a backup is absent. Explicit offline mode skips remote Git observation and reports `not_requested` while retaining local recovery and labels.
- Detached-directory recovery is explicit rather than an automatic repair. `vulcan vault recover-git` requires a device-local registration, an intact materialized worktree, an absent registered Git directory, and a regular `.git` pointer that still names exactly that directory. It recreates an empty detached repository with the recorded platform policy, captures the complete worktree under a unique recovery ref, and only then configures and fetches the supplied `origin`; it performs no checkout or reset. A mismatched pointer or existing Git directory fails closed. The report names hidden Vulcan ref namespaces that may have held unpushed objects which cannot be reconstructed from the shared worktree, and warns that uninstalling Termux can remove private Git data while leaving an Obsidian-visible shared-storage vault.

## Merge policy, structured resolution, and whole-tree validation

- Merge policy is a versioned backend contract, not ad hoc daemon behavior. Ordered rules match portable case-sensitive Git-path globs plus content-aware file kinds, with fixed v1 defaults that permit future structured handling for Markdown, JSON, Canvas, and Bases while requiring review for Obsidian device state, binary data, and unmatched inputs. Its canonical hash is included in conflict identity and sync commit trailers. A device-local automation ceiling is deliberately outside that shared hash and may only replace an automatic policy result with required review; it cannot select a different tree.
- Configuration preserves that ownership boundary: `.vulcan/config.toml` may provide one complete `sync.merge_policy` plus shared `sync.tree_validation` ceilings, while `.vulcan/config.local.toml` may provide device-only `sync.merge_automation` and the default-off `sync.agent_auto_accept` gate. Shared automation/agent-acceptance settings and local policy or whole-tree-limit replacements are diagnosed and ignored. Alternate-index snapshots and worktree pre/postconditions always exclude the local config and rebuildable cache files, independent of user ignore rules, so device policy cannot enter canonical live history or create false worktree drift. The application layer resolves and validates the effective options before creating a transaction journal, so direct CLI, daemon, and companion execution use the same policy and malformed vault configuration cannot silently fall back during synchronization. An embedding caller's own review ceiling is combined restrictively and cannot be relaxed by config.
- Structured resolution is a second pass after ordinary Git merge and configured attribute drivers. It reads immutable base and candidate blobs, bounds input size and nesting, and supports recursive JSON objects, append-only arrays, stable-ID JSON Canvas arrays, Bases YAML, and Markdown frontmatter only when the Markdown body itself has an unambiguous three-way result. `.obsidian/**` remains device-local required-review state under the built-in policy; a complete shared replacement policy may opt narrowly selected Obsidian or plugin JSON paths into the bounded JSON merger, while unknown state never becomes automatic merely from its extension. Deletion and absence are distinct from failure. Every path left conflicted by Git must resolve under the same shared policy before an exact alternate-index tree may be committed; unsupported kinds, syntax errors, overlapping scalars, ambiguous mode changes, and delete/modify conflicts preserve all original conflict inputs. Where concurrent additions need ordering, candidate commit object IDs provide an arrival-independent order. Reports name the file kind and policy rule used for each automatic resolution, while a device-local review ceiling prevents automation without altering the shared policy identity.
- Deterministically convergent artifact formats use that same second-pass boundary through a closed, versioned merger registry rather than acquiring sync-specific implementations. A registered merger declares exact path/media/format versions, whether it is commutative and role-independent, its structural and resource limits, deletion and compaction semantics, and validation/evidence contracts. Append-only event or database-change transports should prefer one immutable actor/sequence- or content-ID-named record per path, letting ordinary Git merge directory union without executing a driver. A packed event set may merge only by validated stable-ID union with canonical ordering; the same ID with different bytes, a missing predecessor/checkpoint, incompatible schema, invalid signature or digest, or a physical delete/modify remains a preserved conflict. A CRDT document merger may join two valid states and canonically serialize the result only when the pinned format proves convergence and idempotence; logical tombstones inside the document are not equivalent to deleting the artifact from the file tree. This registry is Vulcan-owned: apps and repositories cannot provide executable merger code merely by declaring a file type.
- The same registry may be exposed as a plumbing command for ordinary Git. A repository-scoped setup workflow installs narrowly named `merge.vulcan-<format>.driver` commands and plans explicit shared `.gitattributes` rules; it never globally claims generic extensions or silently rewrites existing attributes. The low-level driver reads Git's base/current/other temporary files, determines the format from an explicit registered selector and the conflict path, writes the current file atomically only after successful validation, and follows Git's `0` resolved, nonzero unresolved, and greater-than-`128` driver-failure convention. Because Git's external driver protocol does not supply stable candidate commit identities, only mergers proven independent of side labels and invocation order are eligible there; existing structured mergers that use commit IDs for deterministic tie-breaking remain internal. Installation, status, and removal are dry-run-capable, preserve unrelated Git configuration, and `sync doctor` verifies that every tracked `merge=vulcan-*` attribute resolves to the expected Vulcan executable and supported merger version. A complementary Git mergetool adapter may present the same deterministic attempt before human editing, but it does not claim to resolve structural Git conflicts that Git never passes to a content driver.
- Git and configured attribute drivers remain authoritative for clean text merges. Paths still unresolved afterward receive a stable classification covering overlapping text or binary content, delete/modify, rename/rename, directory/file, case-collision, device-local state, unsupported objects, and ambiguous shapes. The classification records the content kind, matched shared rule, configured action, effective required-review action, and a machine-readable diagnostic code. It is emitted in the finite report and persisted beside each immutable conflict artifact, so CLI, daemon, companion, and future agent workflows do not parse localized Git prose or mistake a failed structured attempt for permission to choose a side.
- Structured results carry explicit validation evidence. Before the merge commit or live-ref compare-and-swap, the backend has already enforced repository-path safety, parsed the selected syntax, checked Canvas and Bases root/entry shapes, kept a Markdown body's link-bearing surface byte-equivalent, rejected conflicted-file deletion, and reread the exact blob bytes and modes from the produced tree. The application-layer validator then enumerates immutable local, remote, and proposed trees through typed Git operations, parses every bounded Markdown blob with the effective vault configuration, and rejects any unresolved or ambiguous authored link not already problematic in either candidate. It also compares the union of candidate paths to the result under shared `sync.tree_validation` limits; both the absolute count and percentage ceiling must be exceeded before a merge is rejected, allowing ordinary small deletions while stopping mass-loss results. Successful reports add whole-tree link and deletion evidence, while failure returns to preserved-conflict handling before a merge commit or remote update. Immediately before every bootstrap, fast-forward, or merge push, the backend also rebuilds the complete worktree tree and requires it to equal the captured candidate; intervening editor writes therefore cause a fresh finite-cycle attempt while the remote ref remains unchanged.
- `vulcan-app` persists interruption-sensitive sync transaction journals under the platform Vulcan user-state directory (`XDG_STATE_HOME` or the platform/home fallback), keyed by the canonical materialized worktree. Journals are versioned, bounded, and atomically replaced; they never live in `.vulcan/cache.db` or the synchronized tree. A later daemon projects and advances the same reusable state rather than introducing a second transaction format.
- The direct sync doctor composes read-only `GitEngine` diagnostics with `vulcan-app` journal and cache inspection. It reports the resolved Git CLI/version, layout and operation safety, readable and agreeing hidden refs, remote reachability, advisory lock ownership, required filters/LFS availability, ignored cache files, retained recovery state, and cache/file inventory coherence without creating a repository, cache, ref, or state directory. Finite cycles perform the same tracked-path filter inspection before capture or remote access: each declared filter must have a process driver or both clean and smudge drivers, and Git LFS must also be executable. The successful report retains the typed readiness evidence; an unavailable driver fails as unsupported repository configuration before any sync ref can encode unfiltered bytes. A typed immutable-tree preflight uses the registered platform profile (or the native profile for an unregistered path) rather than the host running the test: case-fold and canonical-Unicode aliases plus Windows-reserved components are error-level incompatibilities, while non-representable executable modes, link-file symlinks, and filesystem-dependent long paths remain explicit bounded warnings. Finite direct and daemon cycles use the same recorded profile and retain both local and accepted preflights in successful reports. They capture an incompatible local tree, journal its object ID, and publish it only to that device's safety head before stopping; it never reaches canonical live or the worktree of another device automatically. An incompatible pulled or merged tree is rejected before canonical publication or worktree application, leaving current bytes and the accepted remote unchanged.

## Conflict preservation and resolution

- Unresolved Git merges receive deterministic conflict identities derived from the versioned policy hash, merge base, order-independent candidate tips, and sorted conflicted paths. Structured concurrent additions likewise order by immutable candidate object identity, so swapping local/remote roles or trigger arrival order cannot change a resolvable tree. No wall-clock timestamp, arrival position, or model confidence participates in winner selection. Before a conflict is surfaced, base/local/remote commits are anchored under create-only `refs/vulcan/conflicts/<id>/` refs. For bounded regular-file conflicts with a unique base, Vulcan constructs a safe projection: normal clean merge results are retained and the already accepted remote object remains provisionally at each original conflicted path, but no synthetic conflict artifacts enter the canonical vault. Structural objects fail closed to refs and device-local artifacts. A reproducible two-parent conflict-record commit is anchored at the sibling local `record` ref and carries the conflict ID, merge base, device, profile, policy, and immutable sources in trailers; when a safe projection exists that commit anchors its exact tree rather than Git's marker-bearing conflict tree. Vulcan publishes that immutable commit under `refs/heads/__vulcan-sync/conflicts/<id>/record`, compare-and-swap publishes the same provenance commit as the live ref, then applies and verifies it through the ordinary Git-native worktree transaction before reporting the conflict; stale live refs or worktree drift restart or fail closed. Reports and durable records explicitly distinguish published and applied projections. A pre-existing preservation ref that names any other commit is a hard failure rather than an overwrite. `vulcan-app` writes an immutable record and byte-preserving per-side artifacts beneath the device-local sync state directory, including projection metadata, provenance ref, and revision. These device-local artifacts never appear in the vault or Obsidian index, while the refs keep every original Git tree and creation provenance reachable independently of local state retention. Reviewed side and proposal resolutions keep the immutable original merge inputs, lease publication against the live provenance commit, parent the resolution from it, and publish a sibling remote resolution ref. Resolution commits similarly carry the conflict, chosen side, device, policy, and source trailers.
- `vulcan sync conflicts [<id>]` is a read-only projection over that state for either the selected path or `--wiki <id>`. A preserved divergence is an immutable conflict session whose bounded path pages carry deterministic resolution-group identities: ordinary blob conflicts are independent, structural changes remain conservatively atomic, and whole-tree validation failures remain indivisible. Mutable per-batch records beside the session bind an exact group selection, expected accepted revision, output tree and commit, recovery witness, and prepared/published/applied/needs-rebase state without rewriting the evidence. Unpublished work whose lease moved becomes rebase-required and may replan only if selected inputs are unchanged; published work can be applied through a verified later accepted descendant. The initial serialized sync report also stays bounded: its backend and durable-record conflict projections carry counts, completeness flags, at most 16 path/classification previews, bounded diagnostics, and a `detail_conflict_id` rather than embedding an arbitrarily large record; a projected worktree application likewise retains its aggregate action counts but serializes at most 16 path plans with explicit total and completeness fields. Each completed application report includes versioned, content-free `operational_stats` for this cycle: automatic and preserved path/group counts, formatting-candidate count, logical preserved-input bytes, an optional transaction-local Git subprocess count, and coarse whole-cycle/backend/conflict-state/cache timings. The counters never enter conflict identity, journals, or immutable evidence. Summaries expose total path/group and pending-group counts plus an explicitly complete-or-truncated 16-path preview; detail exposes derived group progress. Callers follow `detail_conflict_id` with `sync conflicts <id>` and can request `--path-offset` plus `--path-limit` for an explicitly bounded response. Current manifests read only overlapping evidence pages and expose `returned_groups` plus `groups_complete` beside global counters; older records retain a compatibility scan. Evidence pages split on serialized bytes and count, aggregate digests stream, and explicit path-count and diagnostics ceilings are checked before allocation or publication. The companion capability contract advertises the same 256-path page and 128-group batch ceilings. Unpaged detail remains complete rather than silently truncated. Supersession is durable metadata beside the immutable record, never deletion or a fabricated resolution. A replacement may supersede an older session only when it covers every pending or rebase-required path; independent obligations and legacy grouped sessions remain actionable. Human list/detail output explains editor, local-side, and remote-side workflows with dry-run guidance. It does not reconstruct conflict state from `cache.db` or require the daemon.
- `vulcan sync resolve <id> --side base|local|remote` is the deliberately narrow lossy-side mode. The selected side replaces only paths Git left conflicted, retaining clean three-way results. Repeatable `--group <group-id>` narrows that choice to complete bounded resolution groups: each batch overlays only its selected paths on the current accepted live tree, verifies that those provisional inputs have not changed, validates the exact whole tree, publishes through compare-and-swap and batch-specific refs/trailers, and leaves unselected groups actionable across restarts and unrelated live advancement. Reviewed complete-file resolutions use repeatable `--file <conflict-path>=<source>` arguments instead. Reviewed file, patch, and editor modes may also select complete groups with `--group`: a version-4 proposal binds the sorted group set, selection digest, and exact accepted frontier, overlays reviewed blobs on that frontier, verifies that no unrelated tree path changed, and uses the same durable group-batch publication and recovery transaction. Unlike side selection, reviewed proposal bytes never silently replan after the frontier moves. Dry-run validates exact files, applicable structured syntax, preserved state, worktree, and remote lease without constructing Git objects. This reviewed boundary accepts internal Obsidian state and binary bytes without disclosing them to a provider, and may create a regular file at a Git-synthesized rename destination whose three recorded sides are absent. A reviewed `--patch <file>` is interpreted against the immutable original local candidate through typed Git plumbing: check mode uses a temporary index and writes no repository objects, application requires the patch to touch exactly the selected complete-group paths, and only those non-deleted blobs are overlaid on the pinned accepted frontier. Deletion and unsupported rename/copy forms are rejected. Explicit `--editor` mode materializes conflict-ID-scoped base/local/remote markers for only the selected paths in a private temporary directory, invokes the standard `$VISUAL`/`$EDITOR` command parser, and rejects unchanged files or residual Vulcan markers before treating the cleaned results as supplied files; its dry-run performs all preflight checks but never launches the editor. Patch preparation and editor planning carry their captured selection/frontier into proposal creation, so movement during human review fails stale rather than rebinding the reviewed result. Before any mutating resolution queries the remote, Vulcan captures the current worktree under conflict-scoped recovery refs; it rejects stale worktrees, altered preserved refs, staged/index operations, and unsafe accepted-frontier changes. Prepared resolutions are durable and resumable, publication uses compare-and-swap, application follows remote acceptance, and completed state lives beside rather than inside the immutable conflict record. Terminal and rejected proposal records remain immutable audit history but do not prevent a later proposal. There is no implicit winner. Conflict classification may expose a conservative `formatting_candidate` review hint for whitespace-equivalent text sides, but the hint fails closed on formatting-sensitive Markdown and never weakens `require_review`. An explicit `sync format-propose` may operate only on selected formatting-candidate groups: it requires execute permission, an absolute formatter executable, an exact `--version` pin, optional explicit hashed configuration, bounded arguments/bytes/time, and formats private copies of base, local, and remote before requiring their normalized three-way merge to be clean. The executable, version, arguments, and config identity are bound into a review-only proposal on the captured accepted frontier; the command never accepts or applies that proposal.
- Agent-assisted resolution begins at a provider-neutral `vulcan-app` boundary only after a durable conflict exists. The synchronous provider receives bounded exact base/local/remote bytes plus policy identity and explicitly permitted focused context; immutable sides are inventoried in three batched Git reads independent of selected path count. Git’s `cat-file --batch` headers are parsed incrementally, so per-blob and aggregate limits reject declared oversized content before allocation, and the proposal-specific remaining budget is passed through each side read before provider invocation. Logical per-path accounting also rejects repeated paths sharing one object before cloning those bytes. A request may select up to the bounded complete-group limit; permission checks, eligibility, side inventories, provider disclosure, output coverage, and byte accounting then apply only to those paths, so unselected internal or binary conflicts are neither exposed nor disqualifying. The request and version-4 proposal identity bind the sorted groups, selection digest, and exact accepted remote/live frontier. Named permission profiles gate Git and every exposed path, internal Obsidian/Vulcan state and binary/missing selected inputs are excluded, and broad context is an explicit capability rather than ambient filesystem access. Explicit focused files are symlink-safe UTF-8 reads, sorted and deduplicated, sent with exact bytes and hashes, and retained as hash/size proposal inputs. A provider-neutral tool boundary adds fixed-call/fixed-byte `vault_read`, `vault_search`, `vault_query`, and `vault_links` operations; indexed operations apply `PermissionFilter` before materialization and policy hooks before disclosure, while full-file reads outside explicit context additionally require the caller's `--allow-broad-context` opt-in. The OpenAI-compatible adapter handles bounded tool turns; the distinct reviewed supplied-file path is local and performs no network or tool access. Proposal identity binds tool names, exact argument/result hashes, and returned paths without retaining tool-result content. Retained version-3 records continue to receive their original integrity verification. A provider cannot claim a context path that was neither supplied nor returned by a tool. Output must resolve exactly the selected conflicted paths within byte limits and cannot request deletion. Vulcan constructs an unreferenced proposal tree over the pinned accepted frontier, rereads every selected blob and mode, renders a bounded patch, verifies the worktree, remote frontier, and all preservation refs remained unchanged, and runs the same effective-config whole-tree link/deletion validator used by deterministic merging before atomically retaining a versioned `ResolutionProposal` outside the vault/cache. The proposal records explanation, referenced context, provider/model, prompt/tool contract versions, immutable conflict/policy inputs, path hashes, and validation evidence. Provider execution releases the repository mutation lock, is cooperatively cancellable, revalidates under a fresh lock, permits one ready proposal per conflict, and never writes the worktree or any ref. Approval has a read-only preview and a separately locked application transaction: it rejects stale inputs, unsafe Git state, moved live refs, invalid syntax, altered objects/patches, changed whole-tree validation policy, newly broken links, excessive deletions, an explicit rejection record, or a tree that cannot be reconstructed from the preserved merge; captures recovery state before remote access; publishes only with a lease; applies only the accepted proposal commit; and records a deterministic audit event without prompts, explanations, patches, or note content. Rejection is a separate previewable, idempotent, repository-locked transaction which retains the proposal and all original objects, writes only a deterministic content-free audit decision, and permanently closes that proposal ID against approval. The direct CLI exposes generation through `sync propose`, including repeatable `--group`, rejection through `sync reject`, exact approval through `sync resolve --approve-proposal`, and the composed manual transaction through `sync resolve --file`. Companion creation accepts the same group IDs and explicit accepted target while keeping provider configuration server-side. `sync propose --auto-accept` is a deliberate two-factor policy exception to human review: it is rejected before provider execution unless the caller also enabled device-local `sync.agent_auto_accept`, then persists the proposal and runs the exact ordinary approval transaction; failures leave the proposal reviewable and success uses a distinct content-free `auto_accepted` audit action. Credentials come only from an explicitly named environment variable, while endpoint access is permission-gated and responses are bounded exact JSON. Configurable retention, cross-device claiming, and additional provider protocols build on these boundaries rather than bypassing them.

## Checkpoints, retention, epochs, and publication retries

- `vulcan sync checkpoint [<wiki>] --kind recovery|semantic` anchors the currently accepted live commit under a unique local `refs/vulcan/checkpoints/<kind>/<ulid>` ref. It requires the profile's local, fetched, and pending refs to agree with the exact remote live ref, serializes creation with other repository mutations, never advances the semantic branch, and creates no new Git objects. Recovery and semantic classes are retention intent; both remain immutable object reachability anchors until a later explicit retention workflow removes them.
- `vulcan sync retention-plan [<wiki>]` is the read-only boundary for that later workflow. It first requires the same exact accepted-ref and remote agreement as checkpoint creation, then uses typed ref enumeration and bounded first-parent traversal to report active-epoch pressure, retain the newest configured recovery checkpoints, classify only older recovery refs as expirable, and list semantic checkpoints as permanent. Planning never deletes refs or creates objects. In particular, it does not claim that deleting checkpoint refs prunes snapshot commits which remain ancestors of the canonical live tip; rollover and archive expiry are separately reviewed decisions.
- `vulcan sync retention-apply [<wiki>]` always recomputes under the repository lock and deletes each expirable recovery ref only through its exact planned object lease. Its default remains checkpoint cleanup only. Explicit `--rollover` additionally requires an over-limit epoch, exact accepted/remote agreement, an unchanged captured worktree, no staged state, and no in-progress Git operation. It deterministically anchors the old live tip under both `refs/vulcan/epochs/live/<profile>/<epoch>` and the fallback remote branch `refs/heads/__vulcan-sync/epochs/<profile>/<epoch>`, creates a reproducible parentless commit with the identical tree and protocol/archive trailers, then changes live only through compare-and-swap. Repetition accepts only the same archive/root identities; interruption before accepted-ref updates is repaired by ordinary finite sync. Semantic refs are never changed.
- Epoch archive expiry is a separate explicit reduction of the offline reconciliation horizon. `--epoch-archives-keep <n>` is at least one and plans against the verified trailer-linked chain, newest first; missing local state while a remote archive still exists marks the chain incomplete and prevents expiry classification. `--expire-epoch-archives` deletes only planned older entries, remote first and local second, with exact object leases. That order leaves a local recovery anchor if remote deletion succeeds immediately before interruption, and both completed halves plus repeated application converge safely. A root whose local and remote predecessor refs are both absent is the intentional truncated boundary. Live and semantic refs are never rewritten, while a device older than the chosen horizon receives an explicit error and retains its captured worktree rather than being merged as unrelated history.
- A device that edited from the retired epoch does not force old ancestry back into live history. On divergence, finite sync scans the bounded first-parent chain for the active epoch root, fetches the named archive into its matching local durable ref without overwriting a different object, and verifies that the archived predecessor and root have the same tree. It constructs a private bridge whose parent is the archived predecessor and whose tree is the current remote live tip, merges the offline capture against that bridge, and publishes the validated result as a one-parent child of the current new-epoch tip. Sequentially reconnecting offline devices repeat this operation even after earlier devices have advanced the epoch; unresolved content still enters the ordinary preserved-conflict workflow.
- A rejected live-ref compare-and-swap does not immediately fail or busy-spin. The finite Git cycle recaptures the worktree, re-queries and fetches the live ref, recomputes ancestry or a merge, and retries up to the configured bound with deterministic exponential waits from 25 ms through a 400 ms cap. Cancellation is observed before and after every wait. Repository serialization is shared with resolution and checkpoints; daemon trigger coalescing remains a scheduler concern.

## Branch lane, safety gates, status, identity, and worktree application

- Normal-index and Git-operation safety gates protect reconciliation and application without sacrificing recoverability. Staged changes sync as ordinary worktree bytes through the alternate index while the normal index is never staged, reset, or rewritten; only merge/rebase/cherry-pick/revert/bisect state or an unexpected HEAD commit or symbolic-ref change pauses the cycle. When such a state is present, Vulcan first captures the worktree to its local candidate ref, publishes its per-device safety head, and fetches an existing remote live tip, then emits a structured pause reason and retains the paused transaction journal. It does not push canonical live, apply, reset the normal index, or reinterpret a branch switch. A safety change detected after remote acceptance anchors that accepted commit under the pending ref before pausing application.
- Each finite cycle publishes its pre-operation worktree to the remote device safety head, then fetches and, when possible, pulls the checked-out branch from its upstream before the canonical hidden live ref moves, using the user's own pull configuration (`pull.ff`, `pull.rebase`, `branch.<name>.rebase`) with `--no-edit` and no implicit autostash. If the pull changes the checkout or enters conflict, the resulting bytes are captured and published again; a divergent same-device history is bridged, keeping the pre-pull state reachable. Divergence past `pull.ff=only`, an interactive rebase request, or a merge/rebase conflict pauses the branch lane with a reason; a dirty worktree the pull must not overwrite defers to the next cycle. Repositories without an upstream, detached HEADs, and bare repositories skip with a reason. Immediately after a healthy branch pull lane, the branch tip is published to its upstream with the tracking ref observed during the attempt as an exact lease — never force-pushed — before conflict-prone canonical file reconciliation begins. Ordinary committed history therefore continues to fetch, pull, and push when the file lane later preserves an unresolved conflict. A moved remote reports for the next cycle, while transport or policy failures remain explicit branch-lane failures without preventing the file lane from proceeding.
- Remote device safety heads are operator-visible recovery state, not automatic merge inputs. `vulcan sync devices list` enumerates exact heads, `devices fetch <id>` anchors a selected head and current live under local recovery refs and reports `same`, `integrated`, `contains_live`, or `diverged`, plus changed paths and isolated-worktree guidance. `devices prune-backup <id>` (with `remove` retained as a compatibility alias) cannot prune the current device backup, requires those exact fetched recovery refs, rechecks the remote objects, and deletes with an exact lease only when the candidate is an ancestor of live or has the same tree. Pruning a backup does not revoke device, Git transport, or vault access. Divergent or live-ahead device information fails closed; remote deletion deliberately retains the local recovery ref. This gives another node the tools to resolve a lost device's conflicts without silently mixing its files into canonical live.
- `sync status` is a read-only preview, not a retained daemon-job status or a completed finite cycle. It queries remote refs, previews the checked-out branch, compares the worktree with its last local snapshot, and classifies the hidden file lane as up to date, locally changed, remotely different, changed on both sides, missing on one side, or uninitialized. Registered status also reads durable conflict records and reports unresolved retained conflicts separately from the current file-lane comparison; an accepted/materialized lane can be current while historical conflict choices still require review. Failure to inspect retained conflict state is explicit and makes the overall inspection incomplete rather than silently assuming zero conflicts. It does not fetch remote objects, merge, apply, or claim that differing trees are conflict-free. Human output labels the operation and its successful items as a preview/inspection, states that no changes were applied, and must not render the internal `planned` outcome as though synchronization itself succeeded.
- The currently implemented first mutating sync atomically creates one Crockford-Base32 ULID in device-local sync state and reuses it as the Git actor identity across vaults; dry-run and doctor only read it and never initialize state. Roadmap 12.15 supersedes new identity creation with the cryptographic device contract in `docs/specs/device-identity.md`: one locally generated Ed25519 SSH keypair, a device ID derived from its canonical public-key blob, no continuity between keys, dual-reading of legacy IDs, and no destructive relabelling of existing refs or provenance. Roadmap 12.16 and `docs/specs/device-key-custody.md` then separate the public identity from its active private-key provider: protected file and native system secret are concrete no-fallback choices; the generic exact-key SSH agent is interactive-only. Same-key migration checks dependent operations, retains the old copy for separate cleanup, and does not change identity. Vulcan-created live snapshot, live merge, recovery snapshot, and conflict-resolution commits use concise non-semantic subjects plus parseable trailers for sync protocol version, device, profile where applicable, policy version/hash, immutable source revisions, conflict identity where applicable, and `Vulcan-Sync-Semantic: false`. This provenance is Git-reachable and never depends on `cache.db` or note frontmatter. Key derivation and custody alone do not authenticate a remote claim; signing, trust, ownership, revocation, and SSH transport authorization remain later explicit layers.
- Worktree application has two durable witnesses with deliberate ordering. Vulcan first persists the device-local transaction journal, then writes a versioned `vulcan-sync/apply.json` marker inside the private Git directory before the Git engine mutates files. The marker identifies the transaction, repository, pre-apply snapshot revision, and accepted revision; it survives failed or interrupted application, gives future watchers a stable self-generated event identity, and is cleared only after post-application tree verification. `sync doctor` treats a retained or malformed marker as an error and directs the next cycle to recapture and verify rather than trusting partially applied bytes.
- Before application, the Git engine derives a typed plan from the immutable expected and accepted commits. Each changed path is classified as add, update, delete, or type change and retains its expected/target object ID, mode, and kind without loading blob contents. Immediately before Git's alternate-index worktree update, Vulcan stages the complete current tree through normal Git clean filters and requires its tree ID to equal the expected revision exactly; this is the delete/overwrite precondition and also detects untracked or filtered drift outside the planned path set. Git performs the materialization without touching the user's normal index, after which Vulcan verifies the complete result against an isolated temporary index seeded from the accepted tree before scanning the cache; consulting the normal index here would misclassify target-added files as untracked. The returned application plan makes destructive scope visible in JSON reports and remains independent of an installed-Git versus future embedded engine implementation. The versioned public Git-engine conformance harness builds its seed and bare remote with ordinary Git, gives the selected engine exclusive ownership after clone, and checks stable capture, normal-index isolation, local and remote ref leases, live and custom-ref transport, divergent-conflict classification, safe application and drift rejection, plus ordinary-Git object/ref readability. Journal interruption and repository locking stay in the shared application transaction tests rather than becoming engine-specific behavior.

## Semantic history

- Semantic history is a separate, reviewable projection over an accepted live snapshot. `vulcan sync semantic-plan` resolves immutable source and target revisions, requires the target to agree with local and remote live refs, and groups paths deterministically by top-level area, individual file, one complete change set, typed Git change, or separated textual hunk. Change grouping preserves rename pairs (and dependent rename chains) atomically and uses delete-before-add ordering so file/directory transitions remain valid. Hunk grouping splits only safe ordinary modified-file unified diffs at actual hunk boundaries; additions, deletions, renames, type changes, binaries, unsafe shapes, and single-hunk files retain atomic change behavior. Each hunk patch applies to the preceding isolated tree and may change only its declared path. Every strategy constructs and validates each proposal commit through typed Git plumbing and anchors the exact final tree under `refs/vulcan/proposals/semantic/<plan-id>`. Group paths are sorted independently of Git output order, and the selected strategy is retained in the versioned device-local plan beside bounded patches. Version-6 dry-runs expose exact split patches without creating objects or state, while materialized plans still prove final-tree equality. A provider-neutral optional planning boundary receives only bounded exact per-path patches and may propose ordered whole-file groups plus messages; plan records retain provider/model/prompt identity. Its output must cover every accepted changed path exactly once, cannot name other paths, cannot inject reserved provenance trailers, and still passes the same exact intermediate-commit and final-tree checks, so it organizes accepted bytes without inventing content. The first direct adapter uses an explicit OpenAI-compatible endpoint/model, obtains an optional key only from a named environment variable, refuses redirects, permission-checks network access, and accepts bounded exact JSON; `--agent --dry-run` still calls the provider but creates no Git objects or state. `semantic-apply` revalidates source, proposal, target, worktree safety, ancestry, and exact-tree assumptions before compare-and-swap advancing the semantic branch; it never rewrites or advances live sync refs, and after durable application it lease-deletes the redundant proposal ref while the semantic branch retains the exact commits. `semantic-publish` separately revalidates the applied tip and exact target tree, requires the remote semantic ref to equal the recorded source (or already equal the tip), pushes with an exact object lease, and records publication provenance for idempotent retries; it never force-pushes or changes live refs. `semantic-reject` provides the complementary dry-run-first retention decision: under the repository lock it verifies the exact proposal tip, journals `rejecting`, deletes only that ref with an object lease, and retains a bounded rejected plan record for idempotent audit without keeping the proposed history reachable. Dry-run creates no objects, refs, or plan state, and apply/reject/publish transitions are crash-recoverable and idempotent.

## Optional daemon workers

Semantic automation remains a finite synchronous application workflow. `semantic-auto` records when an accepted live revision was first observed, exits while its quiet-period debounce is pending, enforces a maximum batching delay, and composes plan, apply, and optional exact-lease publication only when due. Cron, Forgejo CI, and the daemon may all invoke this boundary; the app layer does not own a resident async loop, and dry-run does not advance scheduling state.

The daemon semantic worker is an opt-in low-frequency adapter around that workflow, not another synchronization engine. Its startup-loaded configuration names an explicit wiki allowlist and bounded quiet, maximum-wait, and polling intervals; it requires the daemon-owned semantic provider, skips paused registrations and repositories with active file-tree jobs, reapplies each registration's Git and provider-network permission profile, and persists only the latest operational report outside the vault/cache. Blocking provider clients are owned across the async runtime boundary so their final destruction happens after Tokio shuts down.

The daemon conflict worker is the corresponding opt-in resolver adapter for a deliberately designated node. It requires both a daemon-local wiki allowlist and each vault's device-local `sync.agent_auto_accept` switch, so configuring a provider alone never authorizes unattended mutation. “High confidence” is an objective eligibility tier rather than a model-supplied score: only pending singleton regular-file Markdown or UTF-8 text overlaps with complete base/local/remote objects and tight per-path and aggregate byte limits are submitted, without broad vault context. Structural, binary, missing-side, device-state, oversized, non-text, stale, or otherwise ambiguous groups remain preserved for review. The worker shares the companion's process-local conflict claim, reapplies Git and provider-network permissions, and enters the existing proposal retention and automatic approval transaction unchanged; exact output coverage, syntax, links, deletion ceilings, tree identity, worktree recovery, and remote leases therefore remain mandatory. It skips paused or actively syncing repositories, processes at most one conflict per wiki pass, persists content-free outcomes outside the vault/cache, and carries provider-error backoff across restart. Resolution commits advance canonical live history for other devices; the separate semantic worker may subsequently organize the already accepted bytes into human-facing branch commits but can never change them.
